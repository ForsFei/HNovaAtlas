## 一个奇怪的巧合

计组篇说过：程序里的地址从 0 开始编。可是多个进程同时运行，地址都从 0 开始——**它们不会撞车吗**？

会撞的。所以操作系统撒了一个善意的谎：**给每个进程一份专属的"假地址表"**——这叫**虚拟内存**。

## 魔法账本：虚拟地址 → 物理地址

进程使用的地址全是**虚拟地址**。内核为每个进程维护一本账本（页表），记录"虚拟页号 → 物理页框"的对应关系，由 CPU 的内存管理单元（MMU）每次访问时**自动翻译**：

```mermaid
flowchart LR
  A["进程 A 虚拟地址 0x1000"] --> T["A 的页表"]
  T --> P1["物理内存 0x8000"]
  B["进程 B 虚拟地址 0x1000"] --> T2["B 的页表"]
  T2 --> P2["物理内存 0xA000"]
```

两个进程的虚拟地址 `0x1000` 完全相同，账本不同，落在物理内存的不同角落——**各自以为自己独占整条街，实际上只是邻居**。

## 这个谎言换来三大好处

1. **隔离**：A 的账本里根本没有指向 B 内存区域的条目，想越界都无从下手。虚拟内存是进程围墙的工程实现
2. **自由**：程序不用关心"物理内存还剩多少、会不会和谁冲突"，只管按自己的逻辑编地址——写程序简单了
3. **超卖**：物理内存不够也能运行更大的程序，见下节

## 物理内存不够了怎么办：换页

16 GB 内存，程序们总共要 20 GB——账本还有最后一招：把**暂时不用的页面搬去硬盘**（交换空间/页面文件），账本上改记"此页在硬盘"；等程序再用到它，再搬回来。

搬回的过程叫**缺页处理**：

```text
程序访问虚拟地址 → 查页表 → 发现"此页在硬盘"
→ 触发缺页中断 → 内核把它从硬盘读回内存 → 程序毫无察觉地继续
```

程序全程不知情——但**速度大打折扣**：内存访问纳秒级，硬盘访问毫秒级起。频繁换页的极端状态有个形象的名字：**颠簸**（thrashing），表现就是电脑卡到像死机、硬盘灯狂闪。

<Callout type="warning" title="这就是「内存不足会卡」的真相">

计组篇说"内存不够系统会把数据临时挪回硬盘"。现在你能讲清机制了：不是简单的"放不下就搬"，而是**虚拟内存按页换入换出**。缓解办法也顺理成章：少开程序（少占页）、加内存条（扩大物理层）。

</Callout>

## 一页有多大

内存按**页**（page）分块管理，通常每页 4 KB。按页而不是按字节管理，账本才能做得小巧：4 GB 内存按 4 KB 分页也只有一百万条目，且分配释放都以页为单位，整齐高效。

| 概念 | 一句话 |
|------|--------|
| 虚拟地址 | 程序眼里从 0 开始的假地址 |
| 页表 | 内核为每个进程维护的翻译账本 |
| MMU | CPU 里自动查账本的翻译官 |
| 缺页 | 账本说"这页在硬盘"，触发搬回 |
| 换页/颠簸 | 频繁搬入搬出导致卡顿 |

## 动手试一试

1. 任务管理器 → 详细信息，添加"提交大小"列——它和"内存"列的差值，就是被换出到硬盘的部分。
2. Windows 设置里找"虚拟内存"（高级系统设置 → 性能），看看系统把交换文件设了多大。
3. 思考：为什么"加内存条"能同时提升速度和流畅度，而"调大虚拟内存"只能防崩溃不提速？（提示：硬盘比内存慢万倍）
