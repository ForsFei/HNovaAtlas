## 为什么按钮不应只靠 Click

上一节的[绑定与变化通知](/knowledge/desktop/wpf/architecture/mvvm/)用 `Click` 调用 ViewModel，是为了单独观察属性、集合和集合项的通知。现在换成一个明确的业务动作：编辑设备报警阈值。窗口只承载输入框和按钮，是否能“应用”由 ViewModel 的状态决定。这里的“设备”只是本地教学模型，**没有连接硬件或发送网络请求**。

运行 `dotnet run --project examples/wpf-command-validation/WpfCommandValidation.csproj` 可以观察窗口。初始已应用值是 50 °C：输入 `abc` 或 `101` 后“应用”保持禁用、错误显示在输入框下方；输入 `68` 后可以应用；应用后同值无法再次提交；输入 `72` 再点“取消编辑”会回到 68。还可以运行 `dotnet run --project examples/wpf-command-validation-checks/CommandValidationChecks.csproj` 检查状态与事件，但独立断言**不运行 WPF 绑定引擎**。

## 命令把“能否做”与“做什么”放在一起

`ICommand` 有 `CanExecute`、`Execute` 和 `CanExecuteChanged`。按钮绑定 `Command` 后，会利用前者决定可用状态，并在收到事件后重新查询；这比在窗口里到处设置 `Button.IsEnabled` 更容易保持规则一致。[Microsoft Learn 的命令概览](https://learn.microsoft.com/dotnet/desktop/wpf/advanced/commanding-overview)也把命令源、可执行状态和执行动作区分开。

本例用最小 `RelayCommand` 承载两个委托。它没有依赖 MVVM 框架，也没有接管 WPF 的 `RoutedCommand` 或 `CommandBinding`。后者适合路由到控件树目标的命令，本例只需绑定 ViewModel 上的两个动作。

```csharp filename="RelayCommand.cs"
public sealed class RelayCommand(Action execute, Func<bool> canExecute) : ICommand
{
    public event EventHandler? CanExecuteChanged;

    public bool CanExecute(object? parameter) => canExecute();

    public void Execute(object? parameter)
    {
        if (CanExecute(parameter)) execute();
    }

    public void NotifyCanExecuteChanged() => CanExecuteChanged?.Invoke(this, EventArgs.Empty);
}
```

`Execute` 再检查一次 `CanExecute`，是为了即使有人从测试或其他代码直接调用，也不绕过条件；正常 WPF 按钮会先根据 `CanExecute` 禁用自身。不要以为修改了某个属性，普通 `ICommand` 的按钮就必然重新查询：当输入影响条件时，要明确发出 `CanExecuteChanged`。本例的命令在 UI 线程处理输入；跨线程发事件与 UI 线程亲和问题留到后续异步阶段。

## 保留输入文本，区分“不能解析”和“未改变”

把输入框直接绑定到 `int CurrentThreshold` 容易把“用户正在输入的文本”“最后一次合法整数”和“真正已应用的值”混成一个状态。比如清空输入框或键入 `abc` 时，转换失败不应被误认为已应用值变成了 0。本例因此用 `ThresholdText` 保存原始文本，`CurrentThreshold` 保存已应用的整数。

```csharp filename="ThresholdViewModel.cs"
public string ThresholdText
{
    get => _thresholdText;
    set
    {
        if (_thresholdText == value) return;
        _thresholdText = value;
        OnPropertyChanged(nameof(ThresholdText));
        OnPropertyChanged(nameof(ErrorText));
        ApplyCommand.NotifyCanExecuteChanged();
        CancelCommand.NotifyCanExecuteChanged();
    }
}

private bool CanApply() => TryGetThreshold(out int value) && value != CurrentThreshold;
private bool CanCancel() => ThresholdText != CurrentThreshold.ToString(CultureInfo.InvariantCulture);
```

`TryGetThreshold` 要求 0–100 的十进制整数。无效输入不能应用；有效但与已应用值相等，也没有第二次提交的意义。像 `050` 这样的文本虽然数值等于 50，“应用”依然不可执行，但“取消编辑”可以把文本恢复成规范的 `50`。这不是异步请求的幂等保证，只是当前**本地编辑状态**的防重复动作。

## 验证规则与界面反馈

同步字段校验由 `IDataErrorInfo` 的属性索引器提供。WPF 的 `ValidatesOnDataErrors=True` 会在源更新时读取错误，默认验证装饰会标出错误输入框；本例还绑定 `ErrorText` 在输入框下方显示**可阅读的具体原因**，不让用户只猜红色边框的含义。[官方 `ValidatesOnDataErrors` 文档](https://learn.microsoft.com/en-us/dotnet/api/system.windows.data.binding.validatesondataerrors)说明了这个验证规则与 `IDataErrorInfo` 的关系。

```xml filename="MainWindow.xaml"
<TextBox AutomationProperties.Name="新阈值">
    <TextBox.Text>
        <Binding Path="ThresholdText" Mode="TwoWay"
                 UpdateSourceTrigger="PropertyChanged"
                 ValidatesOnDataErrors="True" />
    </TextBox.Text>
</TextBox>
<TextBlock Text="{Binding ErrorText}" Foreground="Firebrick" />
<Button Content="应用" Command="{Binding ApplyCommand}" />
<Button Content="取消编辑" Command="{Binding CancelCommand}" />
```

这里显式设置 `UpdateSourceTrigger=PropertyChanged`，因此每次文本变化都会写入 `ThresholdText`，错误和按钮状态随之更新。`TextBox.Text` 默认是失去焦点后才写回源；若忘记此设置，用户可能键入无效值后看到旧的按钮状态，直到移开焦点。[官方写回时机说明](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/data/how-to-control-when-the-textbox-text-updates-the-source)可供对照。真实表单不一定都需要逐字校验；昂贵的服务端校验更不应放进此同步索引器。

本例把格式和范围放在一处：空值、无法解析的文本（包括小数和空格）、超过范围分别有明确提示。`IDataErrorInfo` 与 `CanExecute` 使用同一套解析条件，避免出现“界面显示错误但按钮可提交”。仍应在真正的提交边界再次检查条件，因为按钮的禁用状态不是业务层安全边界。

## 应用、取消和真实异步取消不是一回事

`ApplyCommand` 只在合法且不同的值上把 `CurrentThreshold` 改为新值。改完后 `CanExecute` 变为 `false`，重复执行不会造成第二次状态变更。`CancelCommand` 则把未提交的 `ThresholdText` 恢复到已应用值，并清除输入错误；已应用值不会回滚。

这两个命令现在都是同步的，也没有“提交中”的远端操作。若将来要向设备写值，就会出现超时、取消令牌、重复请求、失败回滚和窗口关闭等新问题；那属于本路线的 UI 线程与异步阶段，不能把“取消编辑”误解为“取消在途写入”。

## 手动走一遍，再看断言边界

1. 打开窗口，确认初始值 50，两按钮禁用。输入 `abc`、空值与 `101`，分别观察文字错误、输入框标记、应用禁用和取消可用。
2. 输入 `68`，应用后已应用值变为 68；继续点击或直接调用同一命令，不应产生第二次提交。输入 `72` 后取消，输入框回到 68，已应用值不变。
3. 独立控制台断言覆盖格式/范围错误、有效变更、`CanExecuteChanged`、提交一次和取消编辑。但它无法证明 XAML 路径正确、按钮视觉状态及时变化或错误装饰能被看见；这几项要在 Windows 桌面运行窗口检查。

## 常见追问

1. `CanExecute` 返回 `false`，为什么 ViewModel 数据变化后按钮仍可能没有及时更新？
2. 输入 `abc` 时，为什么不把已应用的整数属性直接改为 0？
3. `IDataErrorInfo` 的提示与命令的提交条件不一致会造成什么问题？
4. “取消编辑”与取消一个已经发送到设备的异步请求，语义差在哪里？
