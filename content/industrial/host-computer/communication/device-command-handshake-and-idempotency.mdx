## 为什么写一个Start位还不够

前面已经可以通过 MC、S7、OPC UA 读写数据，但“写入返回正常”与“工位动作已经完成”之间还缺一份业务协议。

例如PC写入目标300，再置启动位：设备可能尚未扫描到启动位；可能因互锁拒绝；可能已开始执行但回执丢了；也可能完成得很快，PC下一次轮询只看见Busy=false。仅靠“写成功”和“Busy消失”，无法区分这些情况。

本篇设计一个小型**单命令邮箱**：一个发布者、一个未释放的命令、一份保留结果。它是本课程自行约定的教学协议，不是三菱MC标准的一部分，不是PLCopen标准实现，也不是可以直接接电机的安全程序。下一篇用真实MC回环读写验证它。

## 四种证据分别记录

| 证据 | 回答的问题 | 不能推出什么 |
| --- | --- | --- |
| 通信写入回执 | 本次数据访问有没有正常返回 | PLC程序已经受理业务 |
| 邮箱回复Recorded | 设备记录了这一份候选请求 | 请求一定允许执行 |
| AcceptedId / Running | 指定请求被接受、已进入执行 | 物理动作已达到完成条件 |
| CompletedId / Done | 指定请求达到了定义的完成条件 | 下一次动作也安全、数据永不丢失 |

Rejected表示执行前拒绝，Faulted表示已接受后遇到故障；都不是Done。设备记录请求之后也可以立即给出Rejected，所以“邮箱回复Recorded”不能被界面翻译成“动作成功”。

在实际运动库里也会看到Busy、Done、Error等信号，但它们的触发、复位和保持规则属于各自功能块契约，不应直接套到自定义邮箱。[运动功能块通用规则示例](https://infosys.beckhoff.com/content/1033/tcplclib_tc2_mc2/70043531.html)

## 请求身份不只是一个自增整数

本课将动作身份定义为 `(BootId, RequestId)`：BootId识别控制器运行代，RequestId在该代内递增。请求还带Operation、Target和Version。

- 相同身份、相同完整参数：重复请求，返回原状态，不重新执行。
- 相同身份、不同参数：冲突，不允许悄悄修改正在执行的动作。
- 比已消费编号更旧、但结果已释放：拒绝旧请求，不把它重新当新命令。
- BootId变了：旧代结果和去重记录可能丢失，进入核对流程，不自动重发。

参数比较不能只比目标值：操作类型、配方版本、坐标系、单位等也可能影响动作。本例仅比较完整的六字请求，扩展真实任务时应将这些语义纳入不可变载荷。

示例RequestId使用ushort，1～65535，0无效；到上限报错，不绕回1。BootId在模拟器的Reboot方法中递增；它不是已经实现的跨进程持久化启动代。真实设备需要可靠的启动身份/保持策略，否则整机重启后再用BootId=1会使旧身份重用。

## 先写参数，最后提交，提交后冻结

本课邮箱字段分为候选参数、控制握手与状态结果三组：

| 组 | 主要字段 | 责任 |
| --- | --- | --- |
| 候选参数 | ExpectedBootId、RequestId、Operation、Target、Version | PC写；提交前可分步准备 |
| 控制握手 | Control、ControlAck、ReplyId、Reply | PC发布Control，设备回显处理情况 |
| 状态结果 | CurrentId、State、Result、AcceptedId、CompletedId、HighWater | 设备写，PC读取且关联身份 |

PC必须先确认Control/ControlAck均为0，写完全部候选参数并等待通信回执，最后写一个16位Control=1提交。在握手恢复到0以前不得改候选参数。

设备看到提交后，复制候选参数为独立的当前请求，验证启动代、编号、载荷版本、范围与互锁。以后执行只使用这份已锁存参数，不能不断回读PC仍可能修改的寄存器。

仅写了一半参数不会启动；持续保持Control=1也不能每个扫描周期启动一次。这两个边界比“PC把True写进去后立即写False”更重要。

“参数包一次写入”不是本协议正确性的唯一依据。真实PLC还要验证单字访问、通信区可见顺序、扫描程序的锁存点和候选参数冻结规则；不能因为TCP包完整，就宣称多字业务更新天然原子。

## 四阶段握手，不靠短脉冲碰运气

同一个Control通道支持1=提交请求、2=释放已核对的终态结果、0=控制通道复位。每次只处理一个非0阶段：

```text
PC                         设备
完整写候选参数
Control = 1  ────────────→ 锁存/校验一次，保存ReplyId、Reply
              ←────────── ControlAck = 1（保持）
读取并核对回复
Control = 0  ────────────→ 结束本次控制阶段
              ←────────── ControlAck = 0
```

PC未看到ControlAck，不随意改为0；回复丢失时先查状态。完成一次四阶段控制握手，并不表示动作已经执行完，它只是提交/确认通道已经可以继续使用。

这里的“Control复位”只把邮箱控制字归零；**不复位CPU、不清设备故障、不停止轴，也不释放动作结果**。这些动作不能共用一个含糊的Reset按钮。

Control=2使用同一握手机制，但设备只允许匹配身份及完整参数的Done/Rejected/Faulted结果被释放。运行中发送释放会得到NotTerminal，不会把Busy任务清掉。

## 动作状态与结果保持

```text
Idle ── 记录并通过校验 ─→ Accepted ── 开始 ─→ Running ── 完成条件 ─→ Done
  └── 校验不通过 ─────→ Rejected          └── 执行故障 ──────────→ Faulted
                          Accepted也可能在开始前因互锁变化进入Faulted

Done / Rejected / Faulted ── 匹配的显式结果确认 ─→ Idle
```

AcceptedId只在接受后设置；CompletedId只在Done时设置为当前RequestId。这样PC即使没轮询到短暂的Accepted或Running，也可以从保留的Done与编号确认结果，不要求UI恰好命中某次扫描。

真实完成条件必须由设备任务定义，例如控制器到位、速度条件、工件交接和必要反馈。示例只有模拟计数与状态转移，没有真实位置或传感器；它证明握手逻辑，不证明机械动作效果。

终态保持到PC明确确认，避免“Done只亮一个扫描周期”。这也意味着结果未释放时，新编号得到Busy；不能为了方便下一次启动直接覆盖上一份结果。

HighWater保留本代已消费的最大请求编号。释放结果只清当前结果，不清HighWater，因此旧请求仍不会重跑。但详细结果不再保留，之后查不到不能反推它从未执行。

## 提交超时、动作超时与取消分别怎么处理

| 情况 | 上位机应如何描述 | 是否自动再启动 |
| --- | --- | --- |
| 提交控制字调用前停止 | 本次提交未发出；可能只写过候选参数 | 否，后续重新决策 |
| 控制字可能已发出，回执/状态未确认 | Unknown，保留原请求身份和参数 | 否，查询原请求 |
| 已看到Accepted/Running，但等待期到 | 等待超时，设备可能仍在执行 | 否，不等同停止 |
| 本地CancellationToken取消 | PC不再继续等待/发后续操作 | 否，不等同远程取消 |
| 查询发现不同BootId | 旧代证据不可直接使用 | 否，核对现场状态 |

CancellationToken是协作取消机制，不会替你向PLC发送停止命令。[.NET取消模型](https://learn.microsoft.com/en-us/dotnet/standard/threading/cancellation-in-managed-threads)

如果业务需要取消动作，应另定带身份的取消请求、设备允许取消的阶段、停止类型和最终结果；取消与自然完成竞争时，以设备最终证据为准。本轮没有实现远程Cancel或Stop，不能把停止等待当成该功能已经完成。

对真实设备的外部控制需要设备侧互锁与通信故障处置，不由PC回调或界面按钮单独承担。[三菱MC手册的设计注意事项](https://dl.mitsubishielectric.com/dl/fa/document/manual/plc/sh080008/sh080008ab.pdf)

## 断线恢复先查询，不先重发

假设提交RequestId=7后断线，恢复时携带原BootId、编号与完整参数，读取状态：

- 同代、同编号、同参数，Accepted/Running：继续观察这次动作。
- 同代、同编号、同参数，Done/Rejected/Faulted：记录该终态，决定后续确认，不再执行。
- 同编号但参数不同：冲突，禁止继续假定是自己的动作。
- 没有匹配保留结果：NotRetained，可能未收到，也可能已经执行并释放；不能自动当“没执行”。
- 启动代不同：历史可能丢失，需要结合现场、日志或人工恢复，不凭空补一个新编号再启动。

如果只丢了提交回执，Control可能仍保持1、Ack也为1。查询核对ReplyId后，可以显式将该控制阶段归零，再处理保留结果；归零不是重发提交。

若释放结果的回执丢了，结果可能已经清除。这时应保留先前已经记录的完成证据，不能把“当前查不到结果”改写成“动作失败，需要重做”。

## 快照一致性：状态和编号要来自同一份发布

不能把前一轮的CompletedId、新一轮的State和再下一轮的Target拼成一个“成功”。本例状态块带头尾Revision，要求相同且为偶数，并验证状态与AcceptedId/CompletedId对应。

真实PLC可在更新前标记发布进行中，写完数据后发布一致的完成版本；还需验证单字原子性、读写顺序和更新窗口。版本号回绕可能产生ABA，不能把两个相等的小整数当无限时间范围内的保证。

模拟器通过锁复制快照，负例故意改坏尾版本来检查客户端拒绝。它没有模拟实际PLC的所有撕裂方式，也不声称本机一次批读证明现场原子性。本例发布版本禁止回绕，耗尽需要受控处理，不适合作为无限期运行的成品协议。

## 去重不是跨断电的exactly-once保证

本例只保证：**同一模拟启动代、单发布者、当前结果或保留高水位仍有效时，不重复开始同一请求。**

它没有数据库事务、PC请求持久化、PLC掉电保持日志、多PC仲裁、主备切换或跨工位事务。更没有把“物理动作”和“记录去重结果”做成原子事务；断电恰好发生在二者之间时，不能凭软件宣传补出必然结论。

真实项目应根据风险决定：提交前保存什么、结果何时落盘、保持区多久有效、谁是唯一命令所有者、身份如何轮换，以及哪些情况必须人工核对。网络加锁与请求号也不是身份认证，不能用来抵抗未授权的写入者。
