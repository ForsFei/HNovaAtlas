## Modbus 解决哪一层问题

前面已经会使用 SerialPort 和 TcpClient，但它们只解决把字节送到对方，不能解释“读哪一个状态、写哪一个寄存器”。Modbus 为这些请求定义了数据区、地址、功能码和响应格式。

本节先建立协议模型，下一篇用 [C# NModbus 对象与完整读写示例](/knowledge/industrial/host-computer/communication/nmodbus-tcp-and-rtu-basics/)把它落到代码。不要把 Modbus TCP 当成“向 TCP 流发送字符串 READ”：这是另一套二进制报文。

学习时对照三份官方资料即可：应用协议规定功能码与数据模型，串行指南说明 RTU 等串行模式，TCP 指南说明 MBAP 与事务关联。[Modbus 官方规范入口](https://www.modbus.org/modbus-specifications)

### RTU、TCP、RS-485 不是同一个概念

| 名称 | 所在层次 | 应理解为 |
| --- | --- | --- |
| RS-232 / RS-485 | 电气接口 | 接线、电平、拓扑、方向切换等问题 |
| Modbus RTU | 串行报文模式 | 地址、功能码、数据、CRC 和帧间时序 |
| TCP | 网络传输 | 一条有序字节流，需要应用层识别边界 |
| Modbus TCP | TCP 上的 Modbus 报文 | MBAP 头与功能码/数据，不附加 RTU CRC |
| RTU over TCP | 某些设备/网关采用的封装 | 不能凭名称当成标准 Modbus TCP，要核对设备说明 |

所以“设备有 485 接口”不等于“设备一定支持 Modbus RTU”；“有网口”也不等于“支持 Modbus TCP”。串口服务器、协议网关和原生 TCP 设备也可能有不同的 Unit ID 和路由规则。

## 四个数据区，地址可以重复但含义不同

Modbus 常用四个逻辑数据区。读写属性描述的是协议访问方向，不表示设备内部不能更新这些值：

| 数据区 | 每个点的大小 | 客户端常见权限 | 常用读功能 |
| --- | --- | --- | --- |
| Coil，线圈 | 1 bit | 读/写 | 01 |
| Discrete Input，离散输入 | 1 bit | 只读 | 02 |
| Input Register，输入寄存器 | 16 bit | 只读 | 04 |
| Holding Register，保持寄存器 | 16 bit | 读/写 | 03 |

Coil 0、Discrete Input 0、Input Register 0、Holding Register 0 可以同时存在；功能码帮助确定访问哪个区域，不能只保存一个数字地址而不记区域。

“保持寄存器”也不自动承诺断电保存，是否非易失、是否只读、是否要求解锁，都由设备定义。协议支持写入不代表设备开放所有地址的写权限。

## 最容易出错：40001 与 API 地址 0

设备手册可能用 `00001 / 10001 / 30001 / 40001` 这样的参考编号描述各区首点，而协议 PDU 的地址字段从 0 开始。**先识别手册采用什么记号，再转换，不能遇到数字就统一减一。**

| 手册采用传统参考编号时 | 对应区域 | 发出的 PDU 起始地址 |
| --- | --- | --- |
| 00001 | Coil | 0 |
| 10001 | Discrete Input | 0 |
| 30001 | Input Register | 0 |
| 40001 | Holding Register | 0 |
| 40010 | Holding Register | 9 |

例如在明确上述约定的设备中，读 40001、40002 应选择 FC03、起始 0、数量 2，不是把 40001 作为 UInt16 直接传入。

但如果手册直接写“协议地址 0x0010”，它就是十进制 16，不再减一；六位参考编号、偏移地址和厂商工具中的显示方式也要分别核对。建议点位表同时记录“手册原编号、功能区、API 偏移”，并用一个已知值验证。

还要分清：TCP 端口不是站号，Unit ID 不是寄存器地址，读数量也不是字节数。

## 常用功能码与读写数量

下面把十进制与十六进制放在一起，避免把“功能码 16”误写为 `0x16`：

| 十进制 / 十六进制 | 操作 | 数量/数据约定 |
| --- | --- | --- |
| 1 / `0x01` | 读线圈 | 1～2000 bit |
| 2 / `0x02` | 读离散输入 | 1～2000 bit |
| 3 / `0x03` | 读保持寄存器 | 1～125 个寄存器 |
| 4 / `0x04` | 读输入寄存器 | 1～125 个寄存器 |
| 5 / `0x05` | 写单线圈 | 开为 `FF00`，关为 `0000`，不是任意非零值 |
| 6 / `0x06` | 写单保持寄存器 | 一个 16 bit 原始值 |
| 15 / `0x0F` | 写多线圈 | 1～1968 bit |
| 16 / `0x10` | 写多保持寄存器 | 1～123 个寄存器 |

这是协议上限，不代表某个设备支持所有功能或单次允许这么多点。实际还要满足地址范围、连续映射、设备限制和网关能力。[应用协议 V1.1b3，第 6 章](https://www.modbus.org/file/secure/modbusprotocolspecification.pdf)

批量读取不是越大越好：把一个不支持的“空洞地址”包含进去，整次请求可能失败。多寄存器一起读取也不天然保证设备应用层值在同一时刻更新；需要一致快照时，要看设备是否提供锁存、版本号或其他机制。

## PDU 与两种 ADU

PDU 是功能码与数据；ADU 是加上具体传输所需字段的完整应用报文。相同的读取逻辑，RTU 与 TCP 外壳不同。

### 读取保持寄存器的 PDU

```text
03 00 00 00 02
│  │     └──── 数量 2 个寄存器，不是 2 字节
│  └────────── 起始地址 0
└───────────── 功能码 03
```

这些是实际字节的十六进制显示，不是发出文本字符 `0`、`3`、空格。

### RTU：站号＋PDU＋CRC

站号为 1 时，该请求可以表示为：

```text
01 03 00 00 00 02 C4 0B
│  └──── PDU ────┘ └─ CRC，低字节先发送
└─ 站号
```

串行单播常用站号范围为 1～247；地址 0 是广播语义，通常用于写并且不返回单播响应，不能拿来“广播读取所有设备”。本课程示例不用广播写入。

RTU 不是 CRLF 文本协议，不能套前面串口行解析器。除了 CRC，还存在帧间静默时序；串行指南以 t3.5 表示至少 3.5 字符时间的帧间隔，并对不同速率给出处理要求。普通 WPF 定时器或任意 Sleep 不能冒充该时序。[串行实现指南 V1.02](https://www.modbus.org/file/secure/modbusoverserial.pdf)

例如 9600 baud、8E1 一字符通常含 11 bit，3.5 字符约为 4.01 ms。这只是该配置下的换算，不是所有 RTU 设备统一延时；波特率、校验位、停止位必须以设备要求为准，RS-485 方向切换也需适配硬件。

### TCP：MBAP＋PDU

同一 PDU 的 TCP 请求，设事务号为 1、Unit ID 为 1：

```text
00 01  00 00  00 06  01  03 00 00 00 02
事务号  协议号  长度   Unit └──── PDU ────┘
```

7 字节 MBAP 头包含事务号、协议号、长度和 Unit Identifier。长度 6 表示后面 Unit ID 的 1 字节加 PDU 的 5 字节，不是整份报文长度，也不需要再附加 RTU CRC。

服务器响应复制请求事务号，客户端据此关联事务。它不是工件号，不保证写入恰好一次执行。TCP Unit ID 对网关路由尤其重要，直接设备如何处理要看手册；不要把某个设备常用的 1 或 255 当作所有设备的默认值。[TCP 实现指南，MBAP 与事务管理](https://www.modbus.org/file/secure/messagingimplementationguide.pdf)

标准 Modbus TCP 常用端口为 502；本课程模拟器使用回环临时端口，不占用 502，也不使用网站端口 43110。

## 读到 ushort 以后，才开始解释业务

一个寄存器是 16 bit，协议不会自动告诉客户端它代表有符号数、摄氏度、模式还是浮点数的一半。

| 原始寄存器 | 数据契约 | 业务解释 |
| --- | --- | --- |
| `FF85` | Int16，单位 0.1 °C | -123 × 0.1 = -12.3 °C |
| `012C` | UInt16，单位 0.1 °C | 300 × 0.1 = 30.0 °C |
| `0001 0002` | UInt32，高字在前 | 65538 |
| `41C8 0000` | IEEE 754 Float32，高字在前 | 25.0 |

单个寄存器的线上字节先高后低；RTU CRC 的两个字节却是低字节先发，这两个规则不要混淆。32/64 位数据横跨多个寄存器时的字顺序，则必须依据设备手册，不存在仅凭“Modbus”就通用的浮点解释。

NModbus 返回 `ushort[]` 时已经完成单寄存器的协议解码。不要再不加判断地对每个 ushort 做一次字节交换，也不要直接依赖本机 BitConverter 的字节序。

## 异常响应不等于断线

正常读 FC03 时，响应包含字节数和寄存器值；协议异常则把功能码最高位置 1，例如 `03 → 83`，后面带异常码：

```text
83 02
│  └─ 非法数据地址
└─ 对原功能码 03 的异常响应
```

常见异常码的处理思路：

| 码 | 含义 | 首先检查 |
| --- | --- | --- |
| `01` | 非法/不支持的功能 | 设备支持表、功能区是否选错 |
| `02` | 非法数据地址 | 起始地址、区域、跨界、映射空洞 |
| `03` | 非法数据值 | 数量、请求格式、协议参数；不等于通用业务量程判断 |
| `04` | 服务端处理失败 | 设备状态与故障信息 |
| `05` | 已接受但仍在处理的协议应答 | 按设备和库语义处理，不等于业务已完成 |
| `06` | 设备忙 | 是否允许重试、次数、是否存在副作用 |
| `0A / 0B` | 网关路径或目标响应问题 | 网关路由、下游设备和 Unit ID |

异常响应说明对方返回了可解释的协议错误；没有响应则可能是地址/接线/超时/网络等问题。二者应在日志和界面分开，不要全部显示成“连接失败”。

## 先把点位表写完整

本课程模拟器的 Unit ID 是 1，四个区域各 8 个点，API 地址都是 0～7：

| 区域/偏移 | 含义 | 类型/缩放 | 客户端权限 |
| --- | --- | --- | --- |
| Coil 0 | 模拟 Enable 灯 | bool | 读写，仅修改内存 |
| Discrete Input 0 | 模拟 Ready | bool | 只读 |
| Input Register 0 | 温度 | Int16，×0.1 | 只读 |
| Input Register 1～2 | 浮点示例 | Float32，高字在前 | 只读 |
| Holding Register 0 | 目标值 | UInt16，×0.1 | 读写 |
| Holding Register 1 | 模式值 | UInt16 | 读写 |
| Holding Register 2 | 模拟计数 | UInt16 | 读写 |

写目标值成功，只表示寄存器写入得到正常响应；读回一致，也不证明实际温度已达到目标或电机动作已完成。涉及现场控制时，仍需接受/完成状态、互锁、权限和超时未知结果处理。
