## 从“能读到寄存器”走到“读数可信”

上一节已经用 NModbus 完成八类常用功能码，但拿到 ushort 不代表业务解释正确。本节继续解决四个问题：多寄存器怎样组合、周期读取怎样不重叠、界面怎样标记有效性、写入失败怎样避免重复执行。

配套目录为 `examples/industrial-modbus-monitor/`，包含 Core、Checks 和 Wpf 三个项目。仍固定 .NET 10 / NModbus 3.0.83，链接复用上一节的客户端包装器和本机设备。不会访问真实 COM 或现场控制器。

界面只保留模拟设备场景、启动/停止、数值显示和一个目标输入框；地址、Unit ID 与功能码不开放为任意输入。

## 一个寄存器：先类型，再缩放

NModbus 返回 ushort，表示完整的 16 个原始位。若手册写 Int16、单位 0.1 °C，应先解释为有符号数，再缩放：

```csharp
ushort raw = 0xFF85;
decimal celsius = unchecked((short)raw) / 10m; // -12.3
```

不先转换就除十，会把负温度解释成一个很大的正数；转换成 short 后仍要看比例、单位、无效值和量程。`FFFF` 可能是 -1，也可能是厂商约定的“无效”，不能在缺少契约时决定。

写入反过来，从业务值精确编码。本例目标仅允许 0～100、粒度 0.1，用 decimal 计算十倍；30.05 直接拒绝，不暗中四舍五入成 30.0 或 30.1。是否允许舍入本来就应是明确的业务选择。

输入解析固定小数点规则，不允许千位分隔或指数写法，避免把 `1,5`、`1e1` 等文本在不同系统文化下解释成不同命令。Core 再验证一次，不只依靠 TextBox。

## 两个寄存器：区分字节顺序与字顺序

设一个规范化的 32 bit 数值四个字节依次为 A、B、C、D，A 是最高有效字节。设备可能把两个寄存器按不同方式组织：

| 约定名称 | 第一个 ushort 的两个字节 | 第二个 ushort 的两个字节 | Float32 25.0 的示例原始字 |
| --- | --- | --- | --- |
| ABCD | AB | CD | `41C8 0000` |
| BADC | BA | DC | `C841 0000` |
| CDAB | CD | AB | `0000 41C8` |
| DCBA | DC | BA | `0000 C841` |

这些名称是本教程的明确定义，不保证所有工具的“大小端/字节交换”选项采用相同命名。现场应使用手册、已知量或抓包的黄金向量核对，不能按“哪个看起来像温度”来猜。

Modbus 单寄存器在线上传输时仍按协议高字节在前；表中的 BADC/DCBA 是更高层的多字节数据布局，不是让协议改用另一种寄存器传输格式。

### 先还原 UInt32 位模式，再解释类型

Core 的 `ModbusValueCodec.UInt32` 先将两个 ushort 展开为四个明确的字节，再按所选排列恢复到 ABCD，最后用 BinaryPrimitives 读取：

```csharp
byte[] bytes = [(byte)(first >> 8), (byte)first,
                (byte)(second >> 8), (byte)second];
int[] indices = order switch
{
    RegisterOrder.ABCD => [0, 1, 2, 3],
    RegisterOrder.BADC => [1, 0, 3, 2],
    RegisterOrder.CDAB => [2, 3, 0, 1],
    RegisterOrder.DCBA => [3, 2, 1, 0],
    _ => throw new ArgumentOutOfRangeException(nameof(order)),
};
uint bits = BinaryPrimitives.ReadUInt32BigEndian(
    indices.Select(index => bytes[index]).ToArray());
```

这里故意用容易核对的实现，不提前做复杂 Span 优化；接口不会受当前 CPU 大小端影响。[Microsoft：ReadUInt32BigEndian](https://learn.microsoft.com/en-us/dotnet/api/system.buffers.binary.binaryprimitives.readuint32bigendian?view=net-10.0)

同一位模式解释为有符号整数和 Float32 是不同操作：

```csharp
int signed = unchecked((int)bits);
float measurement = BitConverter.Int32BitsToSingle(signed);
if (!float.IsFinite(measurement))
    throw new FormatException("该测量契约不接受 NaN 或 Infinity。");
```

`Int32BitsToSingle` 是按位重新解释，不是把整数数值强制转换成 float。`(float)bits` 得到的是另一个数；同时，不是所有 IEEE 754 位模式都代表有限测量值。[按位解释 API](https://learn.microsoft.com/en-us/dotnet/api/system.bitconverter.int32bitstosingle?view=net-10.0)、[有限值判断](https://learn.microsoft.com/en-us/dotnet/api/system.single.isfinite?view=net-10.0)

本例 Float32 契约固定 ABCD，UI 不提供容易误操作的动态排列切换；四种排列由离线黄金向量检查。设备需要其他排列时，先改数据契约与检查，再调整界面。

## 位字段与字符串也要有契约

一个 ushort 可能把多个状态放在 bit0～bit15，而不是一个整数计数：

```csharp
bool ready = (status & (1 << 0)) != 0;
bool alarm = (status & (1 << 15)) != 0;
```

位号从哪里开始、某位为 1 表示什么，都看点位表。库读 Coil 返回 bool[] 与“一个保持寄存器里的一组标志位”不是同一个协议操作。也不要对状态寄存器随意整字写入，覆盖其他位。

`ModbusValueCodec.Ascii` 采用另一份明确约定：每寄存器先高字节后低字节、可打印 ASCII、尾部 NUL/空格填充。例如：

```text
4154 4C41 5330 3100 → ATLAS01
```

中间出现 NUL 后又出现正文、非 ASCII 字节等会被拒绝。设备若用 UTF-8、UTF-16、低字节先放或长度前缀，应另写解码规则；ASCII 函数不可能自动识别所有 PLC 字符串。

## 轮询：一个所有者，顺序工作

本轮采用低频教学方案：**每轮建立一条 TCP 连接，在一个后台工作单元里顺序读写，然后释放**。它不是上一节的持续 TCP 长连接，也不伪装成连接池。

这样便于复用已验证的 NModbus 总期限/取消包装器，清楚观察一轮工作的边界。高频采集、连接数量受限或反复建连代价高的设备，应改为明确所有者的长连接；协议数据解释和写入结果模型仍然可以复用。

默认一轮预算 1.5 秒，完成后延时 1 秒；不是严格每秒采样。顺序读取：

```csharp
ushort[] input = master.ReadInputRegisters(1, 0, 3);
ushort[] holding = master.ReadHoldingRegisters(1, 0, 3);
bool ready = master.ReadInputs(1, 0, 1)[0];
```

输入寄存器与保持寄存器是不同功能区，两次请求之间设备可能变化。本例把结果装进一份客户端采样记录，不声称它是设备同一时刻的原子快照；如需一致性，必须由设备侧锁存、版本号或握手支持。

读取失败就清旧采样，有限恢复后重新读取；连续三轮失败进入 Faulted。协议或数据解释错误直接停止，而不是不断重连来掩盖映射问题。

## 写入队列只允许一个命令

目标写入被固定为 Unit1、Holding Register 0、FC06。排队前必须满足：

- 监控正在运行，有不超过 3 秒的新鲜采样。
- 输入在 0～100 且能精确表示为 0.1 的整数倍。
- 没有其他排队或在途写入。
- 没有停止请求。

Core 接收后产生一个应用命令 ID，保存期望原始值和单调排队时间，状态变为 Queued。这个 ID 仅用于本地记录，不等于 Modbus 事务号，也没有被当作设备端去重号。

下一轮取走队列中的命令，发送前再次检查采样有效性；排队超过 2 秒或采样已不新鲜就标记 NotSent，不延迟执行。读取失败或停止也会取消尚未取走的命令。队列规则和轮询状态在同一个短锁内调整，避免刚进入故障又意外接受新命令。

不使用多个 UI 定时器各自调用 master；读取和写入只有同一工作单元能执行，所以不会一边轮询、一边让按钮抢占同一条流。

## 写入状态不能只有 true/false

| 状态 | 已知事实 | 是否自动重发 |
| --- | --- | --- |
| Queued | 尚未发送，等待下一轮 | 否 |
| Sending | 准备调用写方法，停止不能保证撤回 | 否 |
| NotSent | 队列取消/过期，或尚未尝试写入就失败 | 否，不自动重排 |
| Rejected | 写调用得到明确 Modbus 异常 | 否 |
| Uncertain | 写入已尝试，但没有拿到确定回执 | 否 |
| Acknowledged | 写回执正常，但未完成读回验证 | 否 |
| Mismatch | 写回执正常，读回不等于期望 | 否 |
| Verified | 写回执正常且读回一致 | 否；仍不证明动作完成 |

主线很直接：

```csharp
master.WriteSingleRegister(1, 0, command.Raw);
// 到这里才知道获得了正常写回执。
ushort readBack = master.ReadHoldingRegisters(1, 0, 1)[0];
// 比较 readBack 与期望值，得到 Verified 或 Mismatch。
```

但代码还会分别记录“开始尝试”“已收到写回执”“读回是否完成”。如果写完后读回失败，不能退回“完全没写”；如果写调用没有回执，也不能武断断定“没有生效”。停止会保留这些结果，而不是把所有状态清成未发送。

即使读回一致，也可能被其他客户端覆盖、被设备应用稍后调整，或仅说明设定值已更新。它不是工件动作完成、温度达标或安全互锁的证明。

## 最重要的故障：设备改值后回执丢失

内置设备的 `ApplyWriteThenDropOnce` 场景会：

```text
客户端写目标 300
  → 模拟设备确实把 HR0 改为 300
  → 不回写入响应，直接断开
  → 客户端显示 Uncertain
  → 后续恢复读取，看到目标 30.0
```

后续读到 30.0 并不能把旧命令自动改为 Verified：它缺少那次写入的正常回执，且真实系统可能还有其他写入者。代码只恢复读取，不重新排入旧命令；自动检查会验证模拟设备实际修改次数始终为 1。

另一个 `ApplyWriteThenSilence` 检查在设备改值后不回复，再由调用方取消，验证“停止”不会把已尝试写入说成“没有发送”。这是结果未知问题，不靠多重试几次解决。

## WPF 怎样显示和停止

Core 发布不可变 `ModbusSnapshot`，UI 以 200 ms DispatcherTimer 读取。显示温度、Float32、目标、Ready、模式、计数、原始寄存器与数据龄；超过 3 秒或状态非 Polling 时，读数无效、写入按钮禁用。

Core 的 TryQueueTarget 仍独立验证状态和输入，按钮禁用不是唯一保护。UI 记录最多 100 条状态/写入结果，短于刷新周期的过程可能被合并，不把它当作完整审计日志。[Microsoft：WPF 线程模型](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/threading-model)

停止顺序沿用前面的原则：先禁止新命令并使读数失效，取消运行令牌，关闭正在工作的专用 TCP 并 await 同步库任务，再等待监控与本机模拟器结束。关窗先暂缓，再异步完成清理；不使用 Wait/Result 阻塞 UI。

这些约束只是教学应用逻辑，不是现场安全控制或权限系统。实机还需要设备模式、授权、写入白名单、互锁、业务握手、日志和恢复条件，不能把本机的“写入一次”按钮直接连到电机启动地址。

## 运行与验收边界

从仓库根目录运行：

```powershell
dotnet run --project examples/industrial-modbus-monitor/Checks/ModbusMonitor.Checks.csproj
dotnet run --project examples/industrial-modbus-monitor/Wpf/ModbusMonitor.Wpf.csproj
```

WPF 仅 Windows。默认 None 正常场景；选择 RejectWrites 可看明确协议拒绝，AdjustSetpoint 可看设备调整后的读回不一致，ApplyWriteThenDropOnce 可看结果未知与读取恢复。

Core 检查覆盖四排列黄金向量、符号与缩放、特殊浮点数、ASCII、位字段、输入边界、队列互斥/过期、正常/拒绝/不一致/回执丢失以及取消。它使用真实回环 TCP 和 NModbus，但没有访问真实设备或 COM。

WPF 编译通过与人工点击、视觉检查、实机验收是不同层次，本轮分别记录，不混称“全部验证”。RTU 串口时序、转换器、接线与现场数据兼容仍需指定测试环境。
