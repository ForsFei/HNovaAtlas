## 为什么不能只给上一节加一个 while

上一节每次查询都建立 TCP 连接、发送、读一帧，然后释放。持续监控设备时，经常需要保留连接，周期读取并在断线后恢复。这时至少有四件事必须有明确归属：

- 谁持续从流里取字节、保存半帧，并分发完整响应。
- 每个请求怎样对应自己的响应，迟到或重复报文怎样处理。
- 哪些失败可以恢复、什么时候停止恢复、恢复后哪些数据失效。
- 窗口停止或关闭时，怎样等待收发任务真正结束。

本节仍只做**只读温度监控**，不包含运动启动、设备复位或动作重放。项目为 `examples/industrial-tcp-session/`，.NET 10，无第三方包；内置真实 TCP 回环设备，所有演示都使用 `127.0.0.1` 的系统分配端口。

交互只有场景选择、启动和停止。WPF 不增加复杂面板，重点放在可测试会话与状态。

## 一条连接的所有权

本例划分三个小对象，而不是引入完整驱动框架：

| 对象 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| `TcpConnection` | 一个连接、一个持续接收任务、一个会话解析器、最多一个在途请求 | 自动重连、控件更新、动作恢复 |
| `TcpMonitor` | 建连、心跳/读取周期、有限恢复、最新不可变快照 | 多设备管理、并发请求表、UI 控件 |
| `LoopbackDevice` | 本机教学设备与故障注入 | 真实设备兼容、工业实时性或安全认证 |

窗口拥有整个运行任务和停止令牌。`TcpMonitor` 一次连接成功就创建一个新的 `TcpConnection`；该连接结束后，先 await 清理，再进入恢复等待。新连接不会借用旧解析器或旧待响应对象。

底层仍使用上一节的 `TcpClient.ConnectAsync`、`GetStream()`、`NetworkStream.ReadAsync/WriteAsync`。不要再从另一个定时器读取同一个流，也不要给同一连接的每个请求创建独立接收循环。

## 心跳协议：PONG 不等于温度更新

温度请求保持上一节格式，新增一对应用层心跳：

```text
PING <32位小写十六进制请求号>\r\n
PONG <同一请求号>\r\n

READ <新请求号> TEMP\r\n
TEMP <同一请求号> 253\r\n
```

ASCII 载荷最多 96 字节，CRLF 分帧。每个请求都生成新编号，响应还要与请求类型匹配：等待 PONG 时，即使收到同编号 TEMP，也不能算心跳成功。

这是自定义教学协议。**真实设备不一定支持 PING，不能擅自发送这几个字符。** 现场应使用协议指定的心跳、状态点或安全的只读查询。

TCP KeepAlive 和应用心跳不是同一件事：前者属于传输连接探测机制，具体行为取决于系统与 socket 配置；后者要求设备应用按协议回复。本例没有依赖 KeepAlive 来判定业务通路，也没有把 `Connected` 当实时在线探针。

PONG 只表示本次应用请求得到了匹配响应，不证明运动已完成、设备没有报警或现场处于安全状态。只有新的 TEMP 响应通过格式、量程和请求号校验后，才更新温度采样时间。

## 状态怎样变化

| 状态 | 进入条件 | 温度有效性 |
| --- | --- | --- |
| `Stopped` | 尚未启动，或用户停止完成 | 无有效读数 |
| `Connecting` | 正在尝试建立新 TCP 连接 | 无有效读数 |
| `Online` | 同一会话完成一轮 PONG 与温度响应 | 有值，但仍需检查数据龄 |
| `Retrying` | I/O、EOF 或超时后，已退出旧会话，等待下一次尝试 | 立即清空旧值与时间 |
| `Faulted` | 连续失败达上限，或协议失败 | 无有效读数，需用户检查后重新启动 |

正常路径是 `Connecting → Online`。可恢复故障走 `Online → Retrying → Connecting → Online`；恢复失败过多进入 Faulted。用户停止可以中断建连、待响应和退避等待，停止之后不再自动启动下一轮。

连接代次 `Generation` 只在 TCP 建立成功时递增；连接尝试次数 `Attempt` 每次尝试都递增。二者不是一回事，TCP 建立成功也还没有达到本例 Online 的条件。

## 一个接收循环，解析器跨请求保留

接收器的生命周期和连接一致，解析器不在每次查询后重建：

```csharp
var decoder = new CrlfFrameDecoder(WireProtocol.MaxPayload);
byte[] buffer = new byte[256];
while (true)
{
    int count = await _stream.ReadAsync(buffer.AsMemory(), _life.Token)
        .ConfigureAwait(false);
    if (count == 0)
        throw new EndOfStreamException($"连接 EOF；残留字节 {decoder.BufferedBytes}。");

    foreach (string frame in decoder.Feed(buffer.AsSpan(0, count)))
    {
        SessionReply reply = SessionProtocol.ParseResponse(frame);
        // 在短锁内按当前 pending 的编号、类型和完成状态分发。
    }
}
```

ReadAsync 返回量仍然不等于帧长；非空缓冲返回 0 表示对端有序结束发送且无更多数据，其他网络失败也可能抛 IOException。本协议需要持续双向交换，所以把 EOF 当作会话结束，而不是继续空循环。[Microsoft：NetworkStream.ReadAsync](https://learn.microsoft.com/en-us/dotnet/api/system.net.sockets.networkstream.readasync?view=net-10.0)

相比单次查询，这里不能一找到一帧就把整个解析器丢掉：同一块输入还可能包含重复响应或另一部分字节。接收循环会处理所有帧，并保留未完成部分，直到连接结束。

如果接收任务在轮询间隔内发现 EOF，监控器也会观察它的 Completion，立即进入恢复，不必等下一次发送才处理。网络静默但没有 EOF 时，则由下一轮心跳/读取期限发现问题；不承诺瞬时感知所有断网。

## 怎样让响应完成正确的请求

本例只有一个在途请求，不必提前做并发字典。用一个 `Pending` 保存编号、类型和 `TaskCompletionSource<SessionReply>`：

```csharp
pending = new(WireProtocol.NewId(), kind,
    new TaskCompletionSource<SessionReply>(
        TaskCreationOptions.RunContinuationsAsynchronously));
lock (_gate)
{
    // 完整代码还检查接收任务是否已经失败。
    _pending = pending;
}

await _stream.WriteAsync(SessionProtocol.Request(kind, pending.Id), budget.Token);
SessionReply reply = await pending.Source.Task.WaitAsync(budget.Token);
```

先注册 pending，再写入，防止设备回复很快时接收循环找不到等待者。接收循环不直接修改 WPF，而是完成对应 promise：

```csharp
lock (_gate)
{
    if (_pending is not Pending pending || pending.Id != reply.Id
        || pending.Source.Task.IsCompleted)
    {
        Interlocked.Increment(ref _ignored);
        continue;
    }
    if (pending.Kind != reply.Kind)
        throw new FormatException("响应编号正确但类型不匹配。");
    pending.Source.TrySetResult(reply);
}
```

几个细节要一起看：

- 编号不同或已完成的重复响应忽略并计数，不能拿去更新下一次查询。
- 类型不匹配和非法业务格式使会话失败，不把协议错误伪装成正常读数。
- `RunContinuationsAsynchronously` 避免在接收器的短锁内直接执行等待方的后续逻辑。
- 完成、取消和失败可能竞争，所以使用 `TrySetResult/TrySetException/TrySetCanceled`，并在清理中观察失败任务。
- 发送门 `SemaphoreSlim(1, 1)` 让调用串行化。它限制在途请求，不限制外部排队调用总数；本监控器按顺序 await，不制造无界任务队列。

如果在自己的应用中并发调用 RequestAsync，必须先取消并等待这些调用结束，再释放连接；不要一边释放发送门，一边让其他调用继续排队。本示例由单个监控循环负责请求与释放的顺序。

这里 WaitAsync 等的是内存中的响应 promise。超时后，代码会取消并关闭整个旧连接，再 await 接收任务结束；不是只停止等待一个仍在读取 socket 的后台任务。

## 期限、心跳与轮询节奏

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| `ConnectTimeout` | 2 秒 | 一次建立连接的期限 |
| `RequestTimeout` | 1 秒 | 单个 PING 或 READ 的发送与等待总期限；不包含等待发送门的时间 |
| `PollInterval` | 1 秒 | 一轮成功心跳和读取之后的延时 |
| `RetryBaseDelay` | 250 ms | 连续失败后的初始恢复等待 |
| `RetryMaxDelay` | 2 秒 | 恢复等待的上限 |
| `MaxConsecutiveFailures` | 4 次 | 连续失败达到此值就进入 Faulted |
| UI 新鲜度限制 | 3 秒 | 本示例超过这个数据龄就不再显示为有效温度 |

周期主线是：`PING → 等 PONG → READ → 等 TEMP → 延时 → 下一轮`。每次 I/O 都 await，因此不会像不受控的 async 定时事件那样重叠执行。周期实际耗时包括两次请求和延时，不是精确每秒采样。

如果采用 `PeriodicTimer`，也应由一个消费者循环 await，并理解它的 tick 合并语义，不能把它当作并行定时回调制造器。本例不需要固定 tick，直接在成功周期后 Task.Delay。[Microsoft：PeriodicTimer](https://learn.microsoft.com/en-us/dotnet/api/system.threading.periodictimer?view=net-10.0)

ConnectAsync 和读写均传入取消令牌，连接期限、请求期限和用户取消分别处理。取消是协作机制，不代表工业实时响应时间保证。[Microsoft：ConnectAsync](https://learn.microsoft.com/en-us/dotnet/api/system.net.sockets.tcpclient.connectasync?view=net-10.0)

## 有限重连，不是无限重试命令

本例恢复策略：

1. EOF、IOException、SocketException 或请求超时，结束旧会话；清除 pending、取消接收并释放旧 socket，await 接收任务。
2. 清空温度和采样时间，连续失败计数加一。
3. 未达上限时按指数退避等待；默认前三次分别等 250、500、1000 ms，连续第 4 次失败直接 Faulted。
4. 新建 TcpClient、解析器和请求对象，发新的心跳和只读查询。
5. 只有一整轮 PONG 和温度响应都成功，才清连续失败计数。仅 Connect 或 PONG 成功不清零。

通用等待公式有 2 秒上限，多个客户端同时恢复时生产环境还应考虑适当抖动，避免同步重连。本机单设备演示不额外加入随机行为。

协议格式/类型错误直接 Faulted，不自动反复重连。需要先核对协议、版本和字段，不能把重连当作处理所有异常的通用办法。

**自动恢复连接不等于自动恢复动作。** 本例只重新发新编号的只读请求，没有保存并重发旧请求。如果将来加入启动电机或送料命令，必须先定义设备接受/完成状态、幂等去重、超时未知结果及人工恢复条件，不能把动作塞进这个循环。

## 新会话怎样隔离旧数据

新连接至少要隔离以下状态：

| 状态 | 本例处理 |
| --- | --- |
| 旧接收字节和半帧 | 旧接收器退出后随旧解析器丢弃；新连接创建新解析器 |
| 旧请求等待者 | 请求 finally 清除，失败/取消明确完成；不迁移到新连接 |
| 请求编号 | 每次重新生成，不沿用旧请求号 |
| 温度与采样时间 | 失败、恢复等待、停止时置空 |
| 会话代次 | 每个成功建立的 TCP 连接递增 Generation |

不同 socket 的字节不会被代码主动混用，但设备业务状态仍可能跨连接保留。若设备支持动作或主动上报，还需要协议层的工件号、执行状态或会话握手；不能以“换过连接”证明设备动作已经取消。

## WPF：显示快照，不逐字节更新

Core 使用 `MonitorSnapshot` 不可变记录保存状态、连接尝试/代次、温度、单调采样时间和说明；通过 `Volatile.Write` 发布完整快照，读取方用 `Volatile.Read` 取得同一个对象。

这避免 UI 同时看到“新状态＋旧值＋更旧时间”这样的字段混搭，但不表示所有业务因此都线程安全。请求分发仍有自己的短锁与生命周期规则。

WPF 在 UI 线程上用 200 ms 的 DispatcherTimer 读取最新快照：

```csharp
_refresh.Tick += (_, _) =>
{
    if (!_stopping && _monitor is not null)
        Render(_monitor.Snapshot);
};
```

Render 只有在 `Online`、有温度、且 `SampleAge` 不超过 3 秒时显示有效值，否则显示“无有效读数或数据已过期”。SampleAge 用 Stopwatch 单调时间计算，不把 DateTime.Now 的墙钟变动当成数据新鲜度变化。

后台不持有控件，不等待 UI 回调，也不把每个收到的字节排进 Dispatcher。界面只保存最多 100 条记录；200 ms 之间的短暂状态可能被合并，因此它是状态展示，不是完整审计日志。[Microsoft：WPF 线程模型](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/threading-model)

如果现场需要每个状态变化都可追溯，应额外记录有界/持久化事件日志，不能从这个 UI 列表反推完整过程。

## 停止与关窗的顺序

窗口停止操作先禁止再次启动、使界面读数失效，然后 Cancel 并 await 整个运行任务：

```text
取消窗口运行令牌
  → 取消建连 / 待响应 / 退避等待
  → 退出旧 TcpConnection，关闭 socket 并 await 接收任务
  → TcpMonitor 发布 Stopped
  → 停止并 await 内置模拟设备
  → 恢复按钮，或完成关窗
```

关窗先通过 `e.Cancel = true` 暂缓，避免 Dispatcher 提前结束；等待清理后再允许 Close。重复关闭请求只启动一次停止流程。UI 不使用 `.Wait()` 或 `.Result` 同步阻塞。

完整代码在 `Wpf/MainWindow.xaml.cs` 的 `StopAsync`、`OnClosing`；接收清理在 `Core/TcpConnection.cs` 的 `DisposeAsync`。所有模拟器和接收任务都会被等待，不能只在 finally 中写一句 Cancel 就宣称已经完全停止。

## 运行与故障复现

从仓库根目录运行 Core 检查：

```powershell
dotnet run --project examples/industrial-tcp-session/Checks/TcpSession.Checks.csproj
```

Windows 上启动 WPF：

```powershell
dotnet run --project examples/industrial-tcp-session/Wpf/TcpSession.Wpf.csproj
```

不必单独运行设备进程。窗口启动时创建自己的回环服务和临时端口，停止时一同释放。不会与网站 43110 或上一节手动模拟器 43120 冲突。

| 场景 | 观察目标 |
| --- | --- |
| `Normal` | 多轮心跳与温度复用同一连接，代次保持 1 |
| `DropOnce` | 第一次采样后下一轮断线，旧值失效，第二条连接恢复采样 |
| `IdleCloseOnce` | 首次采样后空闲断开，不必等下一轮请求才观察到 EOF |
| `PartialOnce` | 第一条连接只回半帧；第二条连接不继承残留字节 |
| `SilentPing` | 心跳不回复，有限恢复后 Faulted，不继续读取温度 |
| `SilentTemperature` | PONG 有响应但温度无响应，仍会达到失败上限 |
| `StaleReplies` | 旧编号响应被忽略，正确响应仍可完成 |
| `DuplicateReplies` | 重复响应不误配下一次请求 |
| `Malformed` / `WrongKind` | 格式/类型错误直接停止，不自动重连 |

这些是应用级故障注入。它们不模拟所有网络丢包、路由变化、设备固件或 TCP 实现行为。
