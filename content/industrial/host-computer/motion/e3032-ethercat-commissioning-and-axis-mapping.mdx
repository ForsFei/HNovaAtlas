## 本章要解决的实际问题

上一批已经讲过[运动单位与坐标](/knowledge/industrial/host-computer/motion/axis-units-coordinates-and-profiles/)及 [SDK 常用函数](/knowledge/industrial/host-computer/motion/leadshine-e3032-sdk-basics/)。这一批回答：为什么 SDK 找到卡，轴却仍不能使用？为什么看到“总线正常”，位置却可能来自错误的逻辑轴？

主线是用户确定的 E3032 EtherCAT 总线卡。下面是实机接入前的知识与核对流程，**没有执行现场扫描、参数下载、复位、使能或运动**。没有配套 SDK 和完整设备信息时，先完成清单和离线 C# 诊断示例，不用猜测实际接线或默认参数。

## 1. 先做一页设备与软件清单

| 清单项目 | 需要记录什么 | 为什么影响后续 |
| --- | --- | --- |
| 控制卡 | 完整型号后缀、卡 ID、硬件及固件版本、实际轴配置 | E3032 名称本身不能代替具体配置 |
| PC 软件 | 驱动、SDK 包、配套 LTDMC.cs/DLL、进程位数 | 防止声明、导出和驱动不配套 |
| 伺服 | 驱动器型号/固件、支持的模式、参数备份 | 回零和位置单位依赖驱动器 |
| 总线 | 拓扑、从站清单、ESI 版本、已有配置工程 | 相同数量不等于相同设备和映射 |
| 机械轴 | 逻辑轴名、运动方向、传动比、导程、有效指令分辨率 | 当量与方向不能从网线顺序推断 |
| 信号 | 原点、正负限位、报警、就绪、到位的接入位置及有效含义 | 区分卡 IO、驱动 IO 与总线模块 |
| 安全条件 | 急停、STO、制动器及防护的既有设计与验收状态 | SDK 成功不证明设备安全 |

资料是后续诊断的预期值来源。不要“读到什么就把什么自动当成正确配置”，否则接错卡或改错映射也会被程序接受。

接线遵循所用卡、扩展板和伺服的对应手册：确认供电、总线进出端、接地、屏蔽和接口定义。本文不提供未知型号的端子号或电平接法。不要将控制卡 EtherCAT 端口当普通办公网络端口随意接交换机，也不要因网口灯亮就跳过主站、从站和工程核对。

## 2. 总线状态机与驱动状态机是两条线

EtherCAT 从站通常按 INIT → PREOP → SAFEOP → OP 建立通信。INIT 尚不能进行邮箱/过程数据通信，PREOP 可进行邮箱通信；SAFEOP 阶段可更新输入、输出受设备和看门狗配置约束；OP 才进入正常输出数据交换。SAFEOP 不是对整台机器的安全认证，实际输出行为要看设备配置。[Beckhoff EtherCAT 状态机说明](https://infosys.beckhoff.com/content/1033/el28xx/1036980875.html)

而驱动器还有自己的准备、接通、操作使能、快速停止和故障等状态。即使从站处于 OP，也可能因为安全输入、报警或状态转换条件未满足而不能使能。应用更上层还要区分参考有效、手动/自动模式、互锁以及任务占用。

```text
通信层：卡可访问 → 总线与预期从站正常
驱动层：驱动状态可读 → 操作条件满足 → 请求/确认使能
轴参考：坐标与单位可信 → 回零或参考恢复已确认
任务层：模式/互锁/权限/目标合法 → 发出本次动作
```

不能把这四层压成一个 `Connected=true`。本轮诊断只观察前两层的部分数据，不提供后两层的运动许可判断。

### SDK 输出 4 为什么不是总线 OP

雷赛手册的 `nmc_get_axis_state_machine` 输出 0～7 的轴状态枚举，其中 4 为 OP_ENABLE。这不是 EtherCAT ESM 的 OP 状态值，也不是直接把驱动原始状态字与整数 4 比较。`nmc_get_errcode` 输出 0 则是该接口的总线诊断正常含义，不是“所有驱动已使能”。

诊断日志至少标明：函数名、调用返回码、输出值和所处层次。把三个不同来源的数字都命名为 `status`，很容易在维护时混用。

## 3. 从站数量、总轴数、逻辑轴与节点地址

官方手册第 174～175、181～182 页给出几个不同查询：

| 问题 | 官方接口入口 | 不能据此直接推断什么 |
| --- | --- | --- |
| 有多少从站 | `nmc_get_total_slaves` | 不能证明都是正确型号、序列号或位置 |
| 总轴数 | `nmc_get_total_axes` | 包含总线轴和虚拟轴，不能等同物理伺服台数 |
| 某轴是什么类型 | `nmc_get_axis_type` | 类型正确也不能证明对应预期机械轴 |
| 逻辑轴映射到哪里 | `nmc_get_axis_node_address` | 地址不是位置坐标，也不是设备永久身份 |
| 控制器使用什么模式 | `nmc_get_controller_workmode` | 本手册 0 仿真、1 EtherCAT；读取不等于切换 |

轴类型枚举中，0 为虚拟、1 为 EtherCAT、2 为 CANopen、3 为脉冲、4 为未知。本课程 E3032 总线单轴诊断期望类型为 1；读到 0 不会自动改参数“修复”。

### 一份教学映射表

下面全部为虚构示例，不是 E3032 默认配置：

| 机械名称 | 卡 ID | 逻辑轴 | 从站地址 | 子轴 | 工程单位 |
| --- | --- | --- | --- | --- | --- |
| X 平台 | 3 | 0 | 1001 | 0 | mm |
| Y 平台 | 3 | 1 | 1002 | 0 | mm |

一张卡初始化返回 1，并不意味着其卡号就是 1；一个多轴驱动器也可能让几个逻辑轴关联同一个从站的不同子轴。总线中还可能有不提供运动轴的 IO 模块，因此从站数也不等于轴数。

实际映射表应记录来自已验证工程的值，并与 SDK 读回对照；更换设备或修改工程后重新核对。地址和数量检测能发现部分接错，但识别同型号替换还可能需要额外设备身份信息。

## 4. ESI、PDO、工作模式与单位的关系

ESI 描述设备能力，不等于已经把当前拓扑和 PDO 配置正确下载到主站。配置工程决定了哪些对象参加周期交换、逻辑轴如何关联驱动以及相关同步参数。RxPDO/TxPDO 的方向以从站接收/发送为参照，不要按“我的 PC 收发”理解名称。

先理解已有的 [PDO](/knowledge/industrial/ethercat/communication/pdo/)、[过程映像](/knowledge/industrial/ethercat/communication/process-image/)和 [PDO 映射](/knowledge/industrial/ethercat/communication/pdo-mapping/)。具体驱动所需的对象、位宽、模式与同步条件，仍要回到该型号资料；不拿另一台机器的对象表直接覆盖。

运动数据还要做两次语义核对：

1. 接口读的是指令位置、驱动反馈还是别的计数器？当前值是否有参考意义？
2. 当前 SDK 当量定义的 unit 是什么？是否与驱动单位、电子齿轮和机械换算一致？

“数值在变化”只能说明读到了某个变化量。驱动反馈、实际机械位移和坐标可信度不能由指令位置自动代替。只读发现当量不符时应报告并阻止使用该值，不自动写入预期当量。

## 5. 分步接入顺序

### 第一步：保留工程与身份信息

先保存现有配置、型号、版本和接线记录，确认谁拥有卡资源及设备当前任务。已有设备也可能由其他程序控制，不能为了诊断就随意初始化或关闭其 SDK 资源。

### 第二步：在受控环境用配套工具核对

官方手册要求先用 Motion 软件检测硬件系统。首次接入或拓扑变化时，工程配置与下载是单独的调试操作，不放进每次应用启动的自动流程。下载、复位、修改周期、切换控制器工作模式都可能影响已有设备，须按现场条件有计划地完成。

### 第三步：C# 先做身份与只读诊断

初始化资源 → 列出并核对卡 ID/类型 → 读控制器模式和总线诊断 → 核对从站数、轴范围、轴类型和映射 → 读当量、轴状态/错误、指令位置/速度。

本文所用手册中总线 API 的 `PortNum=2` 是接口参数约定，不是让用户把网线插到“编号2”的任意物理插座。参数含义必须与实际版本一致。

### 第四步：为每个失败留下原始证据

先记录调用错误码、输出诊断值、时间和预期/实际映射，不自动清错。重复清错会掩盖根因；反复复位也不应成为“连接重试”的一部分。恢复读取后仍要重新核对，不沿用旧的绿色状态。

### 第五步：再设计受控的运动验收

使能、回零、小行程定位、停止、限位与故障恢复应逐项验收，并覆盖必要的机械、安全与参考条件。本轮没有执行这一步；完成只读诊断也不能将其打勾。

## 6. 常见现象怎样缩小范围

| 现象 | 先核对 | 不应直接做 |
| --- | --- | --- |
| `dmc_board_init` 返回 0 | 卡/驱动/资源、进程位数和 SDK 版本 | 把 0 当成功后继续访问轴 |
| 卡可读，总线诊断异常 | 供电、链路、拓扑、工程、从站诊断 | 自动下载另一份工程或反复复位 |
| 总线看似正常，但轴是虚拟类型 | 逻辑轴范围、控制器模式、工程映射 | 对该轴直接发定位来“试一下” |
| 轴状态是准备/禁止接通 | 驱动状态条件、报警和既有安全输入 | 自动对所有轴使能 |
| 指令位置与机械位移比例不符 | unit、当量、电子齿轮、机械传动定义 | 在应用里临时再乘一个猜测比例 |
| 某次读取失败，但 UI 仍显示旧数值 | 数据质量、采样时间、缓存失效规则 | 仅凭旧位置判断机械已经停止 |

这张表是排查方向，不是对现场故障的远程定论。日志中保留原始值和版本，再按具体手册解释，避免把所有问题都归为“通信不稳定”。

## 7. 脉冲卡对照：哪些核对项仍然保留

脉冲方案不需要同一套 EtherCAT 从站/PDO 诊断，但仍需要卡身份、逻辑轴、工程单位、方向、参考和信号含义。关键变成脉冲方式、驱动输入、电子齿轮、就绪/报警/到位接线及可用反馈通道。

不能把“没有总线错误”当作脉冲轴健康，也不能将总线轴的状态机接口当成通用脉冲伺服就绪接口。后续脉冲分支按 DMC3000 对应资料单独讲接线概念、卡侧回零和反馈，不混在总线诊断后端中。
