## 手动操作为什么值得单独一章

在[动作观察](/knowledge/industrial/host-computer/motion/csharp-e3032-motion-observation/)中，已经区分定位完成、停止和结果未知。手动点动还有一个特殊问题：动作开始没有固定终点，必须持续回答“谁还在要求它运动”。

本章以E3032总线卡为主，脉冲卡作对照。SDK接口按官方资料核对，片段未针对用户配套库编译或执行，没有连接硬件。可运行的是下一篇的[纯模拟WPF面板](/knowledge/industrial/host-computer/motion/wpf-manual-axis-panel-and-input-lifecycle/)，不能把鼠标处理代码当作现场安全系统。

## 1. 点动和相对定位不是同一件事

相对定位的意图是“从当前位置再走一定距离”；按住点动的意图是“在有效的持续操作意图下沿某方向运动，意图撤销后请求停止”。

不要在界面每刷新一次就再发送一个相对位移：这可能形成累计运动、排队和松开后继续执行的命令。反过来，连续运动接口也不会自动认识鼠标是否松开。

本章涉及的接口：

| 意图 | E3032对应手册中的入口 | 需要注意 |
| --- | --- | --- |
| 配置单轴速度曲线 | `dmc_set_profile_unit` | 速度unit/s，Tacc/Tdec为秒；不是每个UI周期重复配置 |
| 启动连续运动 | `dmc_vmove(card, axis, dir)` | 0负向、1正向，调用后仍需停止流程 |
| 请求普通停止 | `dmc_stop(card, axis, 0)` | 调用确认不等于停止已确认 |
| 观察运行/停止 | `dmc_check_done` | 0运行、1停止；不是原目标成功标志 |
| 查看停止原因 | `dmc_get_stop_reason` | 保留原始值并核对版本和动作上下文 |

来源：[雷赛EtherCAT总线卡官方手册](https://www.leisai.com/upload/file/2025/07/31/%E9%9B%B7%E8%B5%9B%E6%8E%A7%E5%88%B6EtherCAT%E6%80%BB%E7%BA%BF%E5%8D%A1%E7%94%A8%E6%88%B7%E4%BD%BF%E7%94%A8%E6%89%8B%E5%86%8C20250728.pdf)9.3、9.4、9.16节。使用范围、模式与参数还需按实际SDK/固件核对。

## 2. 发指令前先建立单轴所有权

至少区分三类条件：

- 数据条件：卡与轴身份正确、总线与驱动状态可用、数据新鲜。
- 操作条件：模式允许、操作来源有效、轴没有被自动任务或另一发布者占用。
- 机械与设备条件：参考、方向、行程、驱动状态、限位和既有互锁满足对应操作要求。

“手动模式”只是其中一项，不会自动绕过设备约束。反向点动也不应简单当成解除限位的通用办法；限位退出是否允许、沿哪个方向、速度和权限如何限制，要在受控恢复流程中按设备设计规定。

教学模型采取保守策略：窗口激活、手动模式、模拟互锁成立，并且模拟轴已使能/回零/空闲，才允许新点动。它不支持无参考退限位或现场维护模式。实际设备若需要这些操作，应单独设计，不能悄悄把普通点动的检查删除。

### 什么叫“一个所有者”

同一时刻只有一个执行单元决定这条轴的动作，界面只交付意图。按下另一方向不排队反向，不与回零、自动定位竞争；必须先撤销当前意图并观察停止，再接受新的明确操作。

真实SDK若有同步阻塞调用，单纯把停止放进“高优先级队列”也无法抢占已经卡住的调用。需要按厂商线程/超时约束设计执行单元，不能承诺UI一按停止就能即时打断驱动API。

## 3. 按住点动的输入生命周期

```text
确认全部松开 → 接受一次新的按下 → 为本次持有分配身份
→ 只有当前有效持有才续期
→ 松开/丢捕获/失焦/模式变化/互锁丢失/故障：撤销持有并请求停止
→ 观察停止 → 再次确认全部松开 → 等待新的按下
```

这里刻意保留“全部松开再按下”的步骤。窗口重新激活、模式切回手动或报警解除时，即使鼠标还保持按下，也不能自动续跑上一个点动。

每次持有携带本地身份。旧MouseUp、旧续期或上一个窗口实例的回调到达时，只能处理它自己对应的持有，不能停止或延长新动作。这个本地身份不等于控制卡提供事务去重，更不能解决另一进程抢轴的问题。

WPF可使用[鼠标捕获](https://learn.microsoft.com/en-us/dotnet/api/system.windows.uielement.capturemouse?view=windowsdesktop-10.0)跟踪指针离开控件后的输入，但要检查捕获是否成功，并处理[丢失捕获](https://learn.microsoft.com/en-us/dotnet/api/system.windows.uielement.lostmousecapture?view=windowsdesktop-10.0)和[窗口失去激活](https://learn.microsoft.com/en-us/dotnet/api/system.windows.window.deactivated?view=windowsdesktop-10.0)。这些事件处理仍依赖应用能够运行。

## 4. C# SDK调用顺序

下方仅展示接口形态，`approved`表示已审核、单位明确的配置，非本项目现成类型。配套包装层必须先核对；**片段未在本项目针对原生SDK编译或执行**。

```csharp
// 独立的配置步骤：目标轴静止，参数与unit已核对。
short rc = LTDMC.dmc_set_profile_unit(card, axis,
    approved.StartVelocity, approved.JogVelocity,
    approved.AccelerationTime, approved.DecelerationTime, approved.StopVelocity);
if (rc != 0)
    throw new InvalidOperationException($"Set jog profile: {rc}");

// 只在接受一条新的有效点动意图后提交一次，不放进UI刷新循环。
ushort sdkDirection = direction switch
{
    -1 => (ushort)0,
     1 => (ushort)1,
     _ => throw new ArgumentOutOfRangeException(nameof(direction))
};
rc = LTDMC.dmc_vmove(card, axis, sdkDirection);
// 记录调用结果、动作上下文；不把返回成功当作后续停止保证。
```

模型的方向为-1/+1，SDK这里为0/1，所以需要显式转换。配置速度也不等于机械实际速度；速度范围、加减速与停止余量均需按设备验证。

撤销意图后，停止请求与停止观察分开：

```csharp
short rc = LTDMC.dmc_stop(card, axis, 0);
// 先处理本次调用结果，再按期限读取运行状态、停止原因和可信反馈。
// 不在这里立刻报告Stopped、断使能或关闭资源。
```

调用结果不明时保留未知；不要为了“确保停止”无条件并发启动另一个SDK会话或不停重发。应使用已经定义并验收的停止与失联处置路径。

## 5. 软件续期不等于卡侧看门狗

教学示例让有效按住意图定期续期，超期请求停止，用于防止过期回调继续拥有动作。它只能在程序与检查循环继续运行时发挥作用。

若进程崩溃、线程卡住、PC断电或通信断开，UI不会继续处理MouseUp，普通C#定时器也不会独立发送停止。卡/驱动器的失联行为、看门狗、停止策略及安全回路，需要依据实际型号、配置和风险设计另行验证。

不要将演示中的250ms租约理解成“E3032在PC崩溃250ms后一定停止”。本轮并没有配置或验证任何卡侧看门狗。

## 6. 故障解除、清错、使能、恢复参考是四件事

建议将恢复流程拆开记录：

1. 收集原始证据：卡/轴、时间、驱动状态、错误码、停止原因、操作意图、数据有效性。
2. 确认故障源和机械环境已处理，旧持有与排队动作已经撤销。
3. 按该故障/设备定义执行允许的清错或复位，并检查结果。
4. 重新读取状态，按流程显式决定是否使能。
5. 重新判断参考是否有效；需要时按验证过的方法恢复参考。
6. 等待新的操作，不自动重放原点动、相对定位或回零。

### 清轴错误码不是通用“设备复位”

手册给出 `nmc_get_axis_errcode`、`nmc_clear_axis_errcode` 和 `nmc_get_axis_state_machine`。它们分别涉及读取轴诊断、清轴错误码和读轴状态，不能仅凭函数名称认定“清错会修复所有驱动故障”。某种驱动还需要怎样的故障复位和前提，必须查对应资料。

```csharp
// 操作导读，未执行。已有证据与现场条件核对后才允许清错。
ushort axisError = 0;
short rc = LTDMC.nmc_get_axis_errcode(card, axis, ref axisError);
if (rc != 0)
    throw new InvalidOperationException($"Read axis error: {rc}");
// 先保存axisError、状态和上下文，不先清掉再排查。

// 显式、受条件约束的清错步骤；不是启动时的自动循环。
rc = LTDMC.nmc_clear_axis_errcode(card, axis);
// 核对返回码，重新读取诊断和驱动状态；本段不使能、不回零、不重发动作。
```

总线错误、驱动轴错误、机械限位和应用互锁不是同一层问题。`nmc_clear_errcode`、轴清错、板卡热复位也不应混成一个“连接重试”按钮；总线/板卡级操作可能影响更多轴和IO，需要单独评估。

### 为什么不在异常清理中直接失能

失能与普通停止不是同一动作。垂直机构等可能涉及保持力与制动器顺序，不能在 `finally` 中无条件失能或关闭板卡。安全停止、STO、防护与抱闸也不能由SDK名称含“急停”的软件调用替代。

## 7. 脉冲卡保留哪些共同规则

单轴所有权、按住意图、丢事件处理、停止确认、旧命令撤销和显式恢复原则都保留。不同的是：就绪/报警/到位与使能可能来自具体接线和IO，而不是同一套EtherCAT轴状态机。

脉冲分支还需核对脉冲模式、方向、当量、输入极性和驱动清警方式。不能用 `nmc_set_axis_enable` 或 `nmc_clear_axis_errcode` 冒充所有脉冲伺服的通用使能/复位流程。[DMC3000官方手册](https://www.leisai.com/upload/file/2025/07/31/DMC3000%E7%B3%BB%E5%88%97%E7%94%A8%E6%88%B7%E4%BD%BF%E7%94%A8%E6%89%8B%E5%86%8C20250710.pdf)应与实际驱动器接线说明一起使用。
