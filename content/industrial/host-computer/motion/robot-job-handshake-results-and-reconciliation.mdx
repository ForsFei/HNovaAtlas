## 本篇从坐标走向工艺任务

上一批讲了[六轴坐标、姿态与模式](/knowledge/industrial/host-computer/motion/six-axis-robot-frames-posture-and-modes/)。本篇不继续堆运动API，而是把一个实际常见的问题讲完整：PC让机器人执行某件产品的流程，怎样知道它接了哪件、跑到哪一步、结果属于谁，以及断线后该查什么。

以发那科/爱普生为背景，但型号未定。本批设计应用契约，配套[C#任务会话与66项离线检查](/knowledge/industrial/host-computer/motion/csharp-robot-task-session-and-results/)。没有实现机器人控制程序、厂商SDK、TCP/现场总线传输、真实运动或安全功能。

## 1. 远程启动和工艺任务不是同一个协议

先把四层拆开：

| 层次 | 回答的问题 | 不能自动推出什么 |
| --- | --- | --- |
| 通信 | 某次读写有没有按协议完成？ | 对端已接受本工件任务 |
| 厂商远程控制 | 哪个程序/功能被选择或启动，命令结果是什么？ | 整件工艺已按业务要求完成 |
| 工艺任务 | 本请求、工件、配方与当前执行/结果是否一致？ | 所有物理效果都已回滚或安全 |
| 安全系统 | 按工位设计履行安全相关功能 | 可被普通握手位和C#超时替代 |

发那科官方PNS/RSR介绍讨论外部程序控制；OTHER远程启动系列又说明UOP及不同控制器背景。这足以提醒我们先核对启动方式，不足以替某一未知型号确定信号编号或时序。这里只使用公开介绍，未观看登录后视频。[PNS与RSR](https://techtransfer.fanucamerica.com/tech-transfer/fanuc-pns-and-rsr)、[OTHER与UOP系列](https://techtransfer.fanucamerica.com/series/how-to-remote-start-a-robot-using-the-other-method)

爱普生所查Remote Control Reference把命令获取、命令完成/结果、响应获取确认分开。这是特定远程功能的协议，不是本篇自定义工件邮箱，也不能直接映射成发那科UOP位。[官方命令执行时序](https://download.epson.biz/robots/ww/data/html/RemoteControl_Ref80/en/050/050-010/050-010-030.html)

因此，不写“收到Start的OK就把工件标记完成”，也不把某一种协议的脉冲宽度抄成全部机器人通用要求。

## 2. 本课选择的控制架构

本课主线是：PC提出受约束工艺任务，机器人侧经过审核的程序解释任务并执行。六关节、路径、构型、精停、夹具与工艺检查由对应控制系统负责，不由PC每轮发送六个轴的位置。

```text
PC业务任务所有者
    → 通信/厂商适配层
    → 机器人侧任务处理程序
    → 审核后的机器人动作与工艺流程
    → 保留原任务的状态和结果
    → PC按原身份读取、记录、确认
```

上图是责任关系，不是已实现的网络。配套代码只实现PC侧会话观察，输入来自脚本化内存报告。机器人任务程序、发布一致性和厂商映射仍待具体控制器实现。

若PLC已经是工位唯一任务所有者，PC通常负责配方、界面和追溯，不应再独立向同一机器人发第二套Start。谁拥有业务任务、谁能发布和确认结果、调试器何时退出控制，都要明确；进程内锁解决不了跨PLC、PC和示教器的控制权。

## 3. 一次任务先固定哪些字段

| 字段 | 作用 | 变更原则 |
| --- | --- | --- |
| PC会话＋请求序号 | 区分本次业务请求与旧请求 | 同会话不回绕，不因重试改号冒充新任务 |
| 工件身份 | 关联产品与追溯 | 接受后不能悄悄改为另一件 |
| JobId | 选择审核后的工艺流程 | 用白名单，不开放任意程序名或任意运动 |
| 配方版本 | 固定本次工艺参数 | 执行时不能重新取“最新配方” |
| 控制器启动代 | 区分重启前后的执行域 | 变化后旧执行状态不能直接继承 |
| 上下文绑定版本 | 对应程序、坐标/工具定义等审核依据 | 实质变更需新审核，不靠同编号掩盖 |
| 工具与工件系标识 | 解释使用哪一套参考 | 同号也需对应正确的定义及版本 |

这些是本课程的应用字段，并非两个品牌原生都有同名寄存器。真实控制器启动代、序号存储和一致性应由配套程序/适配建立，随机Guid不是设备身份或掉电持久化的证明。

配套代码每个会话只固定一个JobId和配方版本，不收任意XYZ、速度或程序名。绑定编号只表示合同，代码没有读取实际配方、校准数据或审核路径；白名单也不提供安全证明。

## 4. “同一个请求”必须连载荷一起核对

同一请求身份、同一完整载荷重复出现，协议应返回保留状态，不重新执行。同号但工件、配方或工具绑定不同，是冲突，不是参数更新。

不同请求到来而旧请求仍保留时，不应覆盖旧状态。即便旧任务已完成，也要先消费/确认它的结果，再按明确的新请求进入下一件。超时后换个请求号再次发起，会破坏原本可查询的关联。

这里要区分两侧责任：配套PC会话检测快照与自己的完整请求是否一致；它没有实现机器人侧的去重、高水位或持久化。设备侧也必须具备相应行为，才能让整个协议成立。

工件号相同也不等于协议重复。两个不同请求号可以携带同一个工件字符串；是否允许返工、重复检测或再次抓取，应由业务规则审核，不能指望邮箱自动防止所有重复物理操作。

## 5. 把接受、运行和完成拆开

| 状态/证据 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| 本地Prepared | PC冻结了一份请求 | 请求已写到机器人 |
| 发布意图取出 | 本地所有者准备尝试一次发布 | 字节已发出或对端已执行 |
| 通信写回执 | 某次发布调用得到确认 | 机器人已接工件或工艺完成 |
| Accepted | 机器人任务程序报告已接受匹配任务 | 已开始运动 |
| Running | 匹配任务正在执行 | 最终会成功，或每个工步都已完成 |
| Held | 匹配任务暂停/保持 | 任务完成，或可以由PC直接Continue |
| Completed＋结果 | 匹配任务有保留终态及工艺判定 | 当前仍处于相同物理位置或可启动下一件 |
| Rejected | 程序明确拒绝了请求，按契约未进入执行 | 整台机器已停止，或没有其他控制源动作 |
| Failed/Unknown | 执行故障或证据不足 | 物理效果没有发生，或已回滚 |

轮询可能没有看到短暂Running。若机器人侧确实保留了完整身份和可靠终态，后续可以直接读到Completed；这不同于看到一个匿名Done位就猜它属于本件。

ProgramIdle、Busy、Done等单个位都不能独立完成上述关联。尤其Busy从true变false，可能是正常结束、暂停、终止、通信失效或程序切换。

## 6. 执行结果与产品判定分别保存

至少有三个不同结论：

- Completed＋OK：流程正常完成，产品按本流程判定合格。
- Completed＋NG：流程正常完成，但产品不合格；结果仍需追溯和处置。
- Failed：流程执行本身故障，产品状态或物理效果可能尚未确定。

本批C#中Completed必须带Ok或Ng；没有判定不填写默认OK。Rejected和Failed使用明确代码，不能把它们标为产品合格。

对真实工位，“完成”还应明确是否包括夹持反馈、测量/检测结果、放料反馈、输出状态以及退出到下一步所需位置。只看到机器人程序走到末尾，不自动证明这些条件满足。

本轮结果含版本、代码和判定，但没有测量值、图片、工件数据库或完整审计。未来增加这些字段时，它们也属于需保留和关联的结果载荷。

## 7. 为什么终态要保留到确认

如果Done只闪一下，PC可能因轮询、调度或断线错过。更适合业务消费的结构是：机器人侧保留终态和结果，直到收到匹配的结果确认；确认包含原请求身份和结果版本，不能只写一个全局Clear位。

```text
机器人：匹配任务完成 → 保留请求＋终态＋结果
PC：读到一致结果 → 验证身份 → 按追溯规则记录
PC：明确消费后发匹配确认
机器人：按协议清空本槽 → 不抹去已要求持久化的历史
PC：观察到本次确认后的有效空槽 → 本地释放本任务
```

释放的是业务邮箱，不是驱动故障、运动参考或安全联锁。产品NG的结果确认也不意味着允许它进入合格品通道。

本批离线PC模型只保留当前记录与最后一条释放历史，没有数据库。演示中的调用者显式取确认意图，不证明结果已可靠入库。需要“先持久化再确认”的生产系统，必须在外层实现这一顺序并处理入库幂等。

## 8. 多字段发布不能靠“我按顺序写了”保证一致

请求身份、工件、配方和发布标志可能跨多个寄存器/报文。对端可能在中间扫描到半份数据；状态和结果多字段读取也可能发生撕裂。

实现时需确定候选区/提交阶段、版本校验或协议提供的一致性机制，并由接收端复制成稳定的任务记录。结果同样需要一致地关联到请求，不能用新请求号配旧Done。

本轮没有规定真实D/DB地址、UOP位、报文布局或PLC/机器人脚本。`Qualified=true`只表示外层声明已经核对了归一化快照的一致性、身份与语义，不是代码自动证明原始总线原子性。

所查爱普生特定远程功能也有无法继续并且可能无当前响应的Malfunction情况。因此“暂时没有结果”不能被通用处理为“任务未执行”。不在未知设备上照抄其复位流程。[官方Malfunction说明](https://download.epson.biz/robots/ww/data/html/RemoteControl_Ref80/en/050/050-010/050-010-050.html)

## 9. 四个容易处理错的丢应答窗口

| 丢失窗口 | 应保留什么 | 不应自动做什么 |
| --- | --- | --- |
| 发布前已明确未尝试 | 本地NotPublished边界 | 宣称机械已停止 |
| 发布后应答丢失 | 原身份、完整请求、可能执行的证据 | 改号重发或重复Start |
| 任务完成但PC未看到 | 查询原任务的保留终态 | 根据Busy=false直接补判成功 |
| 结果确认应答丢失 | 已读到的原结果和确认身份 | 抹掉原完成历史或把下一件当作旧件 |

若后续只读查询取得同一控制器执行域、同一完整请求、有效保留终态，可以补记该原任务的结果；这是新增了明确证据，不是“重连成功所以算完成”。历史中仍应保留曾经的不确定窗口。

配套模型采用保守策略：一旦失联/未知就粘性锁定所有写意图，匹配晚到结果仍可补记历史，但不自动解除锁定，也不自动发结果确认或下一任务。实机恢复流程另行审核，不提供Reset按钮一键绕过。

## 10. 重启、模式切换和暂停怎样对账

PC重启后，新会话没有旧任务历史。即使机器人邮箱看似为空，也不能由此证明上一次任务未执行；要先核对工件、保留任务、执行日志和设备实际状态。新实例不得自动接管另一PC会话的请求。

控制器启动代或程序/工具/坐标绑定改变时，旧快照也不能原样沿用。模式切到示教、远程来源撤销、报警或工艺许可丢失，都应阻止新的普通写意图，并移交现场规定的停止/对账流程。

Held与Failed通常需要核对：关节与实际姿态、程序停点、夹具与工件、抓取/放置是否发生、输出、工艺结果和下一步计划。停止/安全功能由对应系统执行；PC标记Unknown不会停止机械臂。

对账之后是否允许继续旧程序、终止旧程序、重新示教或创建新任务，应按具体控制器和工艺决定。本批没有Continue、Stop、Reset、自动回待机或重新发布功能。

## 11. 接入具体品牌前的验收清单

先确认本体/控制器、软件版本、许可/选件和唯一控制所有者，再确认：如何选程序、请求如何稳定发布、身份怎样保留、接受/运行/终态由谁设置、结果何时释放、重启后哪些数据还在。

分开验收正常OK、正常NG、未执行拒绝、执行中故障、暂停、同号冲突、断线各窗口、两侧重启、模式/工具/工件系变更和结果确认丢失。网络回环、控制器仿真和真实工艺分别记录，不能混为一个“已通过”。

目前只交付通用契约与内存PC观察器；机器人程序、SDK/网络与现场项目仍未完成。接着读[视觉基础与图像采集](/knowledge/industrial/host-computer/vision/imaging-exposure-pixels-and-acquisition/)，把这里的工件/任务身份继续用于图像关联，不因没有指定机器人型号而猜接口。

## 12. 复习与面试追问

1. PNS/RSR/UOP或远程命令应答，为什么不自动等于整件工艺完成？
2. 为什么请求ID相同还要核对完整载荷，确认结果也要包含结果版本？
3. Completed＋NG与Failed分别如何记录、追溯和处置？
4. 发布超时后换一个请求号重发，可能发生什么？
5. 晚到匹配终态能补充哪些历史证据，为什么仍不自动解锁？
6. 空邮箱、ProgramIdle和机械停止之间有什么区别？
7. 如何保证数据库记录完成后才确认结果？本轮示例缺少哪一层实现？
