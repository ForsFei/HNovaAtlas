## 1. 交付不能只有一个exe

上位机交付需要同时说明：发布程序是什么版本、目标机需要什么依赖、现场采用哪份配置、结果写在哪里、出问题时如何留证据和回退。程序能启动，只验证了其中一部分。

本批整理这些材料，并提供可运行的C#资料包示例。示例生成参数模板、维护记录样例、待补现场证据的验收报告、说明和哈希清单；生成的资料包不含工业应用exe、厂商SDK或驱动。工具本身另做了实际win-x64发布与仓库外启动验证，二者不是同一件事。

## 2. 分开发布文件、现场参数和运行数据

| 内容 | 建议位置 | 变更方式 |
| --- | --- | --- |
| 应用发布物 | 按ReleaseId保存的发布目录 | 新版本新目录，保留旧版本 |
| 厂商依赖清单 | 与发布版本绑定的资料 | 标注来源、型号、版本、架构、安装要求 |
| 现场配置 | 独立、受版本管理的站点目录 | 受控修改，记录前后版本和校验值 |
| 工位账本/原图/结果 | 独立数据目录 | 按工件/周期管理，不随升级清空 |
| 日志/维护记录/验收材料 | 独立运行记录目录 | 保留原始记录，另记复测或处置 |

应用升级不应覆盖原工位账本、原图或现场参数。现场配置也不应随意回写进已经封存的发布目录，否则同一个ReleaseId可能对应多份不同内容。

示例资料包是固定四份材料加一份清单的扁平目录。它演示交付材料的完整性检查，不是适用于任意应用目录的通用安装器。

## 3. 选择.NET发布方式

框架依赖发布要求目标机提供匹配运行时；自包含发布把对应.NET运行时一起分发，具体选项见[Microsoft .NET发布概览](https://learn.microsoft.com/en-us/dotnet/core/deploying/)。

```powershell
dotnet publish examples/industrial-station-handover/IndustrialStation.Handover.csproj -c Release -r win-x64 --self-contained false -p:PublishSingleFile=false -p:PublishTrimmed=false -o C:/Temp/AtlasHandoverTool
```

这里发布的是资料工具。实际WPF程序还需要核验Windows桌面运行环境，厂商驱动、许可、相机传输层和原生DLL需分别记录。选择自包含或单文件，并不证明这些厂商组件已安装或ABI匹配。

本批实际执行了框架依赖win-x64文件夹发布，并从系统临时目录调用发布后的exe运行--demo。验证范围是当前电脑，未在干净目标机安装或执行真实设备试验。更完整的模型/原生依赖发布案例见[YOLO发布与CPU探针](/knowledge/industrial/host-computer/yolo/csharp-release-inventory-publish-and-cpu-probe/)。

## 4. 现场参数不能沿用演示默认值

参数模板已知卡族为E3032，卡号、轴号、机械比例、到位误差和速度均为null；PLC端点、地址表版本、相机身份、像素格式、触发关联规则、数据目录与验收标准也留空。

| 参数组 | 需要现场确认 | 不能自动推断的内容 |
| --- | --- | --- |
| 站点/通信 | 站点身份、端点、地址表与协议版本 | 测试地址就是生产地址 |
| E3032运动 | 卡/从站/轴映射、单位、方向、机械比例、反馈/到位与速度约束 | 轴0正确、模型单位就是SDK单位 |
| 相机 | 稳定设备身份、像素格式、Stride、触发映射与采集代 | 第一台相机就是目标设备 |
| 数据 | 明确数据根目录、写权限、容量和保留策略 | 程序所在目录一定可写 |
| 验收 | 质量、位移误差、节拍和长期资源标准版本 | 合成样例通过就是实际质量通过 |

模板只展示部分常见字段。真实配置还要补充驱动参数、电子齿轮、IO/报警、参考策略、工艺互锁等与设备相关的内容。脉冲卡应使用独立适配和参数定义，不能只改CardFamily字符串继续套总线配置。

TemplateOnly保持true；填写完字段也不会变成运行许可。Review只指出缺项、非法数值和模板状态，不连接设备、不验证轴映射或端点是否正确，也不热更新正在运行的工位。

## 5. 交付包怎样清点

```text
handover-example/
  site-parameters.template.json
  maintenance-example.json
  acceptance-report.json
  handover.md
  handover-manifest.json
```

清单记录ReleaseId、固定用途、每个材料的文件名、字节数和SHA-256。只读校验会识别缺失、改动、多余文件、.pending、错误结构和非法文件名；每个文件最多64KiB，目录条目数有上限，不递归扫描其它文件夹。

FilesMatchManifest=true只说明当前材料与这份清单相符。参数仍可未填，现场验收仍可全部缺失；拥有修改权限的人可以同时重写文件和清单，哈希不是认证签名。

本例不自动压缩、上传、安装、覆盖版本或扫描目标机，也不包含设备密码。实际应用的DLL、模型、厂商配置和许可清单应另按明确发布契约管理。

## 6. 维护记录写什么

每次启动检查、事件、参数变更或恢复复核，至少记录记录号、UTC时间、人员、ReleaseId、变更前后配置字节哈希、证据引用和说明。

参数变更应能回答：改前是什么、改后是什么、为什么改、谁观察、测试材料在哪里。不能只写“参数调整完成”；也不应把同一个文件反复覆盖成“最新配置”后丢掉旧材料。

示例MaintenanceRecord有ExampleOnly标志。资料包里的样例明确为离线示例，StartupReview的前后哈希相同，代表没有配置变更；ParameterChange要求前后哈希不同。校验这些字段不证明实际维护发生，也不会解除工位故障或自动发运动命令。

## 7. 升级和回退如何保留现场

升级前保存当前发布清单、现场配置、数据目录信息及未结周期状态；停止接纳新工件，等待实际任务和义务结清。升级后先检查程序/依赖，再核对现场参数和旧周期，按项目规则执行验收。

回退应同时考虑程序和配置兼容性。保留旧exe不代表旧程序能读取新配置或新账本；应事先明确Schema与迁移策略，不支持时停止并保留证据，不通过删除文件解决版本问题。

原图、账本和.pending不随版本回退删除。使用[异常与重启只读对账](/knowledge/industrial/host-computer/station/abnormal-cycle-diagnostics-and-restart-reconciliation/)查看旧周期；对账成功也不替代现场设备和物料复核。
