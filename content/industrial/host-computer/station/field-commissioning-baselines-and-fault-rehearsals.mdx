## 1. 从“离线主链可运行”走向“能在设备上核验”

前面的工位主链、正常留图与异常对账已经交付。它们证明了一些软件规则：同周期身份匹配、迟到不推进、不重复派发、文件损坏可识别。真正接入设备后，还需要确认状态位、单位、时钟、设备启动代和工艺条件是否满足这些规则的输入假设。

本批交付接入方法、八个验收专题和一个C#记录工具。工具运行三项明确范围的离线演练，生成待补现场证据的报告；不会连接设备、安装驱动、修改参数或自动发运动命令。

现场验收条件必须在试验前明确，例如位移误差、允许的图像关联方式、误判/漏判上限、延迟分位数、观察时长及恢复条件。本文不为未知机械、样本和生产节拍编造统一阈值。

## 2. 先固定一份验收基线

一次试验至少记录六组信息：应用提交或发布号；运行时与SDK清单；设备身份和配置版本；通信协议版本；配方/模型版本；样本与验收标准版本。

| 基线内容 | 现场应记录 | 改变后如何处理 |
| --- | --- | --- |
| 应用 | 提交号、发布文件与架构 | 新运行簿，重新评估受影响项目 |
| 运行环境 | OS、.NET、驱动、SDK、原生DLL来源/版本/文件哈希 | 重新核验加载与调用契约 |
| 设备/配置 | E3032型号、固件、从站拓扑、轴映射，相机身份及参数快照 | 重新核验映射、单位和关联 |
| 协议 | 地址表、数据类型、端序、命令/回执与启动代规则 | 重新核验读写及未知结果 |
| 配方 | 定位目标、曝光、ROI、阈值、模型及预处理 | 重新验证对应运动与图像结果 |
| 样本/标准 | 真实样本清单、标注、分组、质量和性能阈值 | 按新标准重新评价 |

C#工具对六段声明计算SHA-256，防止把不同声明混在同一本记录里。这只是声明文本的指纹，不会扫描目标机，也不是SDK、配置或样本文件的实际哈希；清单中应另行列出那些文件的校验值和来源。

## 3. 分层接入，不从完整自动循环开始

建议顺序为：目标机环境核验→只读设备身份/状态→单模块受控试验→明确一次命令和完成观察→工位组合→结果保存与重启→目标节拍长期观察。

通信先核对实际PLC型号、地址范围、变量类型、字节/字序及超时语义。受控写入应使用专门测试变量或台架程序，核验同一命令身份和回执丢失后的处理；TCP连接恢复本身不能证明上一条写入未执行。

E3032先核对卡、总线、从站与轴映射，再核验机械单位、方向、参考和反馈。回零、使能、定位和普通停止各自记录前提与观察结果，不把“函数返回成功”当作“轴已完成”。具体SDK声明和状态值以匹配型号、版本的厂商材料及安装包为准，不能把理想模型字段直接映射过去。

相机先确认身份、接口、像素格式、尺寸和Stride，再核对触发就绪、曝光、帧到达和原帧归属。GenICam提供标准化特征名称，但功能是否存在、可读写及事件支持必须由具体设备确认；参考[EMVA GenICam资料入口](https://www.emva.org/standards-technology/genicam/genicam-downloads-archive/)。

## 4. 八个专题怎样验收

| 专题 | 试验要回答的问题 | 证据示例 |
| --- | --- | --- |
| environment | 目标机加载的是否为预期版本与架构 | 清单、原生加载来源、启动日志 |
| communication | 不确定写入能否保持原命令并只读核对 | 原命令身份、设备回执、执行计数 |
| motion-scale | 轴号、方向、单位、反馈和到位是否符合实际 | 参数快照、独立位移观察、误差记录 |
| motion-stop | 停止、报警、限位、观察丢失后发生什么 | 指令/反馈/报警时间线与恢复记录 |
| camera-correlation | 每次检测的图是否属于该工件和触发 | 设备代、触发、帧身份、异常帧记录 |
| vision-quality | 真实样本上的误判漏判与处理失败是否合格 | 样本/标注/配方、逐图结果与汇总 |
| persistence | 保存失败和进程重开后是否保留不确定状态 | 原图、账本、.pending与只读对账报告 |
| endurance | 目标节拍下延迟与资源是否满足标准 | 件数、时长、分位延迟、峰值/趋势 |

E3032总线卡的拓扑、驱动状态、参考有效性与反馈是重点。脉冲卡还需分别核对脉冲输出模式、每单位脉冲数、方向极性、编码器反馈和外部使能/报警接线；脉冲数发完不等于机械到位。两类设备共享工位身份和结果规则，各自的完成证据应单独确认。

普通停止与独立保护功能分别记录，软件状态机的Stopped不代表真实机械已经停止。具体验证由设备、机械和工艺负责人按现场条件安排，不能用离线按钮状态替代实际观察。

## 5. 故障演练应记录前后链路

每次记录：试验基线、初始状态、注入点、原命令/帧身份、预期现象、实际日志、判定依据、观察人和时间。失败也要保留材料，不直接修改原记录为通过；重新试验使用新运行簿。

| 场景 | 软件应观察到什么 | 避免的错误处理 |
| --- | --- | --- |
| 已发命令、回执丢失 | 原操作保持未知，读取原设备证据 | 无条件再发一次 |
| 定位结果超过业务期限 | 原故障不被迟到成功覆盖 | 迟到后继续拍照 |
| 相机重开/旧会话帧 | 新旧采集代分开，旧帧拒绝 | 用最新预览图补旧工件 |
| 算法异常或无效数值 | 独立处理失败，没有业务NG | 把异常吞掉写成NG |
| 留图/账本保存失败 | 原收据保留、残留材料可核对 | 清空目录后继续生产 |
| 关闭时仍有任务 | 等实际任务和义务结清 | 仅取消等待后就释放资源 |

真实台架演练需事先选定受控注入方式，不能把拔线、改变限位或触发报警当作任何设备都适用的操作步骤。离线可先验证状态与记录规则，再按设备资料制定实际试验。

## 6. 本批实际运行的三项演练

1. 原状态机发出Move后推进模型业务时钟至期限，随后送回成功回复：只结清原Pending，保持Faulted，不产生Capture。
2. 给原状态机送入错误Session回复：保留原Pending，不推进、不重新转移命令。这只是通用身份规则演练，不证明真实相机触发关联。
3. 对不存在账本做实际本地只读检查：报告不可用，路径保持不存在，没有创建目录或设备动作。

三项演练分别附在相关专题的Simulation记录中，只说明对应的小范围演练，不代表该专题全部内容通过。其余模拟记录为空；所有Field记录都为空，报告显示MissingFieldEvidence=8。

## 7. 怎样阅读验收记录

每项分Simulation和Field，记录观察结果、证据引用、UTC时间、观察人及基线指纹。模拟通过不会填入Field，缺失不自动变成Passed，失败记录也不会被后来的不同内容覆盖。

工具不校验引用文件是否真实、不认证观察人，也不依据记录发Start或Review。即使用户填写八项Field通过，记录本身仍不是运行许可；现场验收结论应由实际证据与项目责任流程得出。
