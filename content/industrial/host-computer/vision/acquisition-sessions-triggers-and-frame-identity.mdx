## 从“一张图”进入“一次采集任务”

上一批完成了[成像基础](/knowledge/industrial/host-computer/vision/imaging-exposure-pixels-and-acquisition/)与[Mono8缓冲复制](/knowledge/industrial/host-computer/vision/csharp-mono8-replay-and-buffer-lifetime/)。本篇讨论更容易在现场出错的问题：这张图到底属于哪次触发、哪个工件，以及迟到后还可不可以交给当前算法。

继续按你的选择走相机通用路线。配套[C#单次采集会话](/knowledge/industrial/host-computer/vision/csharp-single-capture-session-and-frame-correlation/)有73项离线检查，使用原合成P2图像，触发关联由夹具人工声明；没有实际SDK、曝光、硬触发或设备能力发现。

## 1. 连接、取流和工件采集是三个生命周期

| 层次 | 建立时要确认什么 | 结束后不应直接推断什么 |
| --- | --- | --- |
| 设备连接 | 选中正确设备、权限和参数可访问 | Close意味着设备里没有旧任务或旧图 |
| 取流/采集会话 | 主机缓冲、回调、设备采集模式和配置一致 | Stop返回就绝不会再收到在途回调 |
| 工件采集任务 | 请求身份、配方、触发关联和目标帧 | 业务超时意味着曝光已撤销 |

一个连接可以有多个取流周期；一次取流可以服务很多工件。设备重启、重新取流、配置变化，都可能让旧图像/旧计数的含义失效。反过来，SDK结果对象已经持有的像素也可能继续有效，不能把资源生命周期和业务可用性混为一谈。

设备关闭、SDK释放和任务标未知分别处理：资源要正确归还，业务要保留原请求的证据，安全或运动停止按对应系统设计处理。

## 2. 通用接入时先找哪些职责

不同SDK名字不一样，但应能在资料中找到下面这些位置，而不是先创造一个万能CameraClient：

1. 枚举/选择设备，按确定的身份打开，不用“发现的第一台”作为生产配置。
2. 核对可读写参数、范围/步进、当前像素格式、尺寸、曝光和触发配置。
3. 建立主机缓冲与收帧路径，按实际SDK顺序启动取流/设备采集。
4. 确认可接受目标类型触发，再根据模式发软触发或等待外部信号。
5. 取得结果，检查成功/完整性、元数据，复制或按规则延长借用。
6. 停止新任务，处理在途结果，按SDK规定停止、关闭并释放。

这是职责清单，不是任何品牌的可直接执行配置步骤。是否支持某种就绪信号、事件或Chunk，必须以实际设备为准；通用路线不承诺所有相机提供相同字段。

## 3. 不要把连续采集和软触发混为同一个开关

设备的AcquisitionMode、TriggerMode、TriggerSelector、TriggerSource之类配置往往属于不同维度。设备持续处于采集状态，仍可能每一帧都等待触发；“Continuous”名称本身不必然表示自由运行。[采集开启与等待触发的例子](https://docs.baslerweb.com/acquisition-start-stop-and-abort)

本课程用三个**应用模式**帮助讨论：

| 应用模式 | 谁决定本次取图时机 | 主要关注点 |
| --- | --- | --- |
| 连续预览 | 设备按当前配置持续产生图像 | 最新画面、丢旧帧策略、显示延迟 |
| 软件单拍 | PC明确提交一次触发意图 | 就绪、调用结果、原请求关联、期限 |
| 外部触发单拍 | 外部控制/运动系统产生信号 | 装载/使能阶段、信号与曝光、计数关联 |

上表不是厂商枚举映射。配套C#仅实现软件单拍的应用观察与关联，不提供连续预览采集器或硬触发输出；这些模式输入不会被默默转换成软件单拍。

## 4. TriggerReady到底表示什么

应问清“准备接受哪种触发”，而不是读一个模糊Ready位。已打开、已启动采集、等待FrameStart、曝光中和可再接受一帧，语义不同。

例如所查Basler资料区分多种AcquisitionStatus，并对软触发状态查询与硬触发Trigger Wait给出不同使用建议。这里是行为对照，不把它的参数套到所有相机。[官方采集状态说明](https://docs.baslerweb.com/acquisition-status)

软件侧做“先查就绪再触发”也不是原子事务，中间状态可能改变。触发调用可能拒绝、超时或得到不明确结果，仍要单独记录。硬触发是否就绪、信号沿/电平/电气要求和外部节拍，则需要设备侧与控制系统共同核对。

任务发起前与实际取触发意图前都应复核就绪。发起后，设备因正在处理本帧而暂时不再Ready可以是正常现象；不要把等待期间Ready=false直接当成失联或再次触发的理由。

## 5. 一次触发至少有这些不同时间点

```text
PC准备请求
    → 本地取出一次触发意图
    → SDK/传输调用及其应答
    → 设备接受目标触发
    → 曝光开始 / 曝光结束
    → 读出 / 传输 / 主机完整收帧
    → 图像关联后交给处理
    → 算法和业务结果完成
```

这条链强调语义，不表示PC总能按此顺序收到所有回调。收帧回调可能先于触发调用回执被应用线程处理；同一设备事件、SDK等待线程和UI线程的调度也不同。

因此，调用应答不能代替曝光证据，曝光事件不能代替完整收帧，完整收帧也不能代替工件判定。给每阶段明确含义，比统一写一个Success布尔值更可靠。

## 6. 四组身份不要互相代替

| 身份 | 典型管理域 | 作用 |
| --- | --- | --- |
| 工件＋业务请求Key | 工位/PC应用 | 本件为什么要拍、用哪份配置 |
| 相机执行/计数代 | 设备适配与启动核对 | 重启/复位前后的计数不能混用 |
| 原触发关联身份 | 经核对的设备/外部触发关联 | 说明收到的帧属于哪次触发 |
| 主机图像会话＋帧号 | SDK接收/自有图像层 | 区分某个具体像素对象和旧回调 |

相机序列号通常标识设备，不等于本次采集会话；FrameId通常标识帧，也不天然是PC请求号。原来的OfflineFrameSource.FrameStamp仍只是主机回放身份。

所查pylon的BlockID说明甚至区分GigE与USB的起点/回绕等语义，不能把“0总无效”或“永不回绕”写成所有设备的规则。[BlockID接口说明](https://docs.baslerweb.com/pylonapi/net/T_Basler_Pylon_IGrabResult)

本轮模型采用外层核对后的归一化TriggerSequence，不是直接读取某个品牌BlockID。它可从0开始，同一设备代严格递增、允许跳号、不允许复用；真实回绕/计数复位需要适配与对账，模型不自行展开。

## 7. 没有可靠触发关联时怎么办

最危险的做法是：工件A超时，开始工件B，然后把下一张图直接贴上B的编号。它可能正是A的迟到图，也可能来自预览、旧缓存或另一触发源。

可靠关联可能需要已确认的设备元数据、外部触发记录、受控采集程序或特定设备协议。仅在回调里增加一个本地计数，再把当前工件号填进去，不会凭空证明关联成立。

还要确认计数到底数什么。例如所查Data Chunks明确某Trigger Input Counter只数硬件触发，软触发/自由运行时不递增，不能拿它作为所有软件单拍的序号。[官方Chunk语义示例](https://docs.baslerweb.com/data-chunks)

配套模型只检查已经被外层证明的关联，Qualified默认false。没有关联时不配图、不自动缓存/排队重新贴标签；请求最终可以超时保留Unknown。真实设备缺少这样的能力时，应先设计并验证受控方案，而不是让算法猜。

单请求串行有助于限制范围，但本身也不证明输入缓冲里没有旧帧。本轮startupReviewed默认false，代码没有真正清空SDK队列或审核在途触发；夹具的true只是声明。

## 8. 设备时间与主机时间要分开

设备时间戳可能是内部时钟ticks，频率、复位和代表的事件需核对；不能直接拿它与Stopwatch秒数或DateTime相减。所查Timestamp资料也单独说明tick频率和复位行为。[设备时间戳说明](https://docs.baslerweb.com/timestamp)

本轮SampledAt和ReceivedAt都是归一化的同一PC单调时钟域：前者用于摘要时效，后者是适配层保留的主机收帧时间。它们不代表曝光时间，也不能据此声称测到了真实触发到曝光延迟。

重复投递同一帧时，不要每次把ReceivedAt改成“现在”来伪造新鲜度。设备时钟同步、曝光时间换算和多相机同步没有在本轮实现。

## 9. 迟到、重复与冲突分别处理

| 情况 | 本轮策略 |
| --- | --- |
| 旧相机代/旧主机会话/别的配置或触发号 | 不配到当前工件，不刷新上下文 |
| 无关联或帧缺触发身份 | Uncorrelated，不以到达顺序猜测 |
| 相同身份、相同像素与元数据重复 | Duplicate，不再次交给处理 |
| 同触发出现另一帧，或同帧身份像素改变 | Conflict，保留原结果并锁定新处理 |
| 本次身份匹配但不完整/资格无效/尺寸错误 | 拒绝处理并锁定复核 |
| 超时/失联后才到的匹配完整帧 | 只记晚到帧元数据，不补判本次成功 |

这些是一个保守单拍模型的应用策略，不是全部SDK必须返回的错误码。多曝光、burst、线扫、多相机同步可能天然一触发多帧，本轮不适用。

## 10. 超时、停止与重连不是自动补拍许可证

触发应答丢失，设备可能已经曝光；收帧超时也可能只是传输或调度较晚。自动再次触发可能拍到已经换位的工件，或产生两张难以区分的图。

本轮未知后锁定新的触发和处理意图；新鲜状态恢复不自动解锁。晚到匹配帧只保留身份元数据，不把旧Unknown改成FrameMatched，不自动启动算法。

Invalidate只是应用声明失效，不调用相机Stop/Abort或清队列。真实SDK的停止/中止还可能受相机型号、采集模式和在途帧影响，不能当成统一“撤回曝光”。[停止与中止行为对照](https://docs.baslerweb.com/acquisition-start-stop-and-abort)

重新连接/取流需要新的主机图像会话和适当设备代/配置核对，还要审核旧工件、旧触发、缓存与结果。不要把new一个会话对象作为对账已完成的证明。

## 11. 和后续算法流水线怎样衔接

已匹配的图像应连同请求Key、工件、配置版本和原帧身份一起交给处理。不能把像素放在队列里，却用一个全局CurrentWorkpiece去接结果。

本轮TakeForProcessing只取一次关联好的自有Mono8图；ReleaseCapture表示应用已经接管该图并释放采集槽，不表示算法成功、产品OK或留图已完成。算法结果、队列容量、保存和WPF显示下一批再建立明确边界。
