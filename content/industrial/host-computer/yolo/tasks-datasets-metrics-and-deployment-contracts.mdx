## 本轮位置：先知道模型要解决什么

这是第11步首批。先讲任务、数据和评价，再用下一篇的C#程序核算手写框；没有下载权重、训练、导出或加载ONNX，也没有把手填预测冒充真实推理。固定模型后的输入预处理、运行时、后处理、WPF和资源验收会分批加入，不增加装饰性交互。

YOLO在这里不是“调用一个万能检测函数”，而是一类视觉模型与相关训练/部署工具。任务、模型代际、类别数量和导出选项都可能改变输入输出。官方资料也分别组织[检测任务](https://docs.ultralytics.com/tasks/detect/)、[数据格式](https://docs.ultralytics.com/datasets/detect/)与[模型导出](https://docs.ultralytics.com/modes/export/)，不能从一个网上例子推断所有模型的张量格式。

## 1. 分类、检测与分割，不是三个精度档位

| 任务 | 回答的问题 | 主要监督信息 | 上位机中典型用途与限制 |
| --- | --- | --- | --- |
| 图像分类 | 这张图/这个裁剪属于什么类别 | 图像级类别 | 已定位工件的外观分类；通常不告诉缺陷在哪里 |
| 水平框目标检测 | 哪些位置存在已定义的目标 | 类别与矩形框 | 找螺钉、定位缺陷候选；框内不一定全是目标 |
| 实例分割 | 每个目标分别占哪些像素 | 每实例掩膜/多边形及类别 | 相邻工件各自的区域；仍要处理粘连、边界误差 |
| 语义分割 | 每个像素属于哪个语义类别 | 像素类别 | 材料/背景/缺陷区域；同类不同工件不一定分开 |
| 旋转框/姿态等扩展 | 倾斜方向、关键点在哪里 | 对应任务的标注 | 拿取姿态或结构点；输出并非普通水平框 |

这里的任务类型不同，不是“分类不够高级就换分割”。例如固定治具上只检查有无，可以先裁ROI再分类；多个零件位置不固定时，检测往往更合适。极细划痕、低对比缺陷和亚像素尺寸测量还要考虑分辨率、照明、光学与算法，不能只换模型名字。

监督检测通常只识别训练中定义的类别。一个未见缺陷没有输出框，不等于工件OK；异常检测/开放集识别也不是本批普通检测器自动具备的能力。

检测适合给传统视觉提供候选ROI。例如先定位零件，再在原图局部做[边缘配对与像素宽度测量](/knowledge/industrial/host-computer/opencvsharp/local-edge-profiles-polarity-and-pixel-width/)。检测框宽度不是精密尺寸，框置信度也不等于毫米测量的不确定度。

## 2. 训练、验证、测试、导出与推理分别做什么

训练用标注样本更新模型参数；验证用来选择模型、阈值和配置；测试在这些选择固定后评估未参与选择的数据。不断查看测试集结果再改阈值，会让它逐渐变成另一个验证集。

导出把模型转为目标部署格式，例如ONNX；推理是用固定参数计算新输入的结果。成功导出不证明C#端的图像处理、通道、输出解释正确；成功执行Run也不证明检测质量合格。

本课程计划用C#与ONNX Runtime承担上位机侧加载和推理。训练/导出工具可以在独立环境完成，不要求生产上位机安装整个训练工具链。ONNX是模型表示格式，ONNX Runtime是执行引擎，二者都不替你决定业务标签、前处理和工件判定。

## 3. 数据集先按“工件与采集来源”分组

工业图像常常高度相似：同一工件连续拍20帧、同一条划痕换曝光拍摄、同一原图裁出多个ROI。逐张随机分到训练和测试，会让模型在测试时遇到几乎看过的东西，分数好看但现场失效。

一个合理的起点是先记录工件/批次/视频/采集时段，再以泄漏风险确定不可拆分的Group；同一Group只属于一个集合。需要跨批次泛化，就保留独立批次；需要适应新相机，就安排对应采集域的验证，而不是只在同相机近重复图中切分。官方[模型测试说明](https://docs.ultralytics.com/guides/model-testing/)也强调独立、未见和实际环境测试。

| 字段 | 建议记录的事实 | 作用 |
| --- | --- | --- |
| ImageId、原始文件校验信息 | 一张原图的身份和来源 | 避免复制文件换名后被当新样本 |
| Workpiece/Batch/Sequence | 物理工件、批次或连续采集组 | 制定分组划分规则 |
| 相机/镜头/光源/曝光/工位 | 采集条件与版本 | 分析域变化和失败集中区域 |
| 标签版本/复核状态 | 谁标、按什么定义标、是否确认 | 避免不同标注口径混用 |
| Split | train/validation/test | 保留冻结的划分清单 |

划分比例没有放之四海皆准的数字。稀有缺陷可能只有少量独立工件，机械地做8:1:1反而无法评价。必须报告每类独立工件数量、负样本数量和采集覆盖，不只报告图像总张数。扩增通常放在训练侧，并保持来源组不跨集合；测试图也随机变换会改变评估问题。

下一篇程序只检查声明的Group是否跨集合，不读取图像内容、不做去重或验证真实工件来源。不同字符串可能实际上是同一工件，程序对此并不知情。

## 4. 标注质量决定指标能否解释

先写类别定义：scratch是任何表面纹理，还是满足某个外观标准的划伤？dent与阴影怎么区分？遮挡、边缘截断、疑似和难例如何处理？人工不一致的边界不能靠训练自动解决。

检测标注尤其需要注意：

- 同一类别的框范围统一，明确是否包含阴影、毛刺或上下文；不能一张紧框、一张大框。
- 已存在但漏标的目标，预测出来可能被评成FP；标错类别也会使匹配解释失真。
- 负样本是经过检查、确实没有目标的图，不是“没来得及标”的图。
- 保留正常样本、困难背景和接近阈值的样本，避免训练只看明显大缺陷。
- 现场临界品应按质量标准复核；检测类别与最终OK/NG判定可以有关，但不必是一回事。

Ultralytics检测数据的常见标签行是：

```text
class_id center_x center_y width height
```

后四项按图像宽高归一化，类别从0编号，类别名与索引对应关系由配置确定。以100×100图中的框(10,10)到(30,30)为例，类别0的一行可以是：

```text
0 0.2 0.2 0.2 0.2
```

这是[官方检测数据格式](https://docs.ultralytics.com/datasets/detect/)的例子，不是本批JSON的格式，也不是所有ONNX模型的原始输出格式。分割标注、旋转框和预测输出不能套这五列。

## 5. IoU：先把坐标口径说清楚

本批程序使用原图上的连续面积边界xyxy：X1/Y1为左上边界，X2/Y2为右下边界，范围分别在0..Width和0..Height。宽=X2−X1，高=Y2−Y1，不加1；它不是“最后一个像素索引”。

```text
intersectionWidth  = max(0, min(A.X2, B.X2) - max(A.X1, B.X1))
intersectionHeight = max(0, min(A.Y2, B.Y2) - max(A.Y1, B.Y1))
intersection = intersectionWidth * intersectionHeight
union = area(A) + area(B) - intersection
IoU = intersection / union
```

两框完全重合为1，不相交为0，仅边接触也为0。20×20框和它内部10×20框的IoU是0.5。非法框、NaN、无穷大和零面积在本例直接拒绝，不通过交换端点或补零“修复”。

如果训练时框定义、导出后的坐标空间、还原到原图的变换不一致，IoU下降可能来自坐标错误而不是模型变差。图像缩放/letterbox、ROI原点和显示缩放将放在后续批次处理，本批不假装已经验证。

## 6. TP、FP、FN怎样从框得到

本批只演示一个固定工作点的简化匹配：先按ScoreThreshold过滤；对每张测试图，按预测分数从高到低，在同类别、尚未匹配的真值中选择IoU最大的一个；达到IouThreshold才记TP。一个真值最多被一个预测占用。

未匹配预测是FP；未匹配真值是FN。重复检测不能都算TP，错类别不能因为框重合就算对；负样本图没有真值，但其中的预测仍然计FP。低于分数阈值的预测记Filtered，不是直接记FP，但它没能覆盖的真值仍可能成为FN。

```text
Precision = TP / (TP + FP)   // 发布的框里有多少匹配正确
Recall    = TP / (TP + FN)   // 应检出的真值里覆盖了多少
```

分母为0时本例返回null，命令行显示undefined。不把没有正例的测试集显示成“召回率100%”。检测任务的背景可生成无数候选框，也不适合未经定义就报“TN很多，所以准确率99.9%”。

当前代码汇总所有类别和测试图片的计数，是micro层面的固定点统计。它没有提供每类AP、宏平均、困难目标忽略、crowd规则或COCO兼容评价；后续真实模型必须与选定参考评价器核对，而不是把这个小程序当官方benchmark。

## 7. 分数阈值、匹配IoU和NMS阈值是三件事

| 参数/指标 | 决定什么 | 不等于什么 |
| --- | --- | --- |
| ScoreThreshold | 哪些预测进入本次评价/发布 | 产品NG阈值、匹配标准 |
| 匹配IouThreshold | 预测与标注多接近才算TP | NMS去重阈值 |
| NMS IoU阈值 | 某种后处理如何抑制重叠候选 | 测试评价的IoU标准 |
| AP/mAP | 在规定规则下总结P-R表现 | 固定分数下的一次Precision/Recall |

AP概括规定类别/匹配条件下的Precision-Recall曲线；mAP再对规定类别及IoU设置汇总。mAP50与mAP50:95不应混报，具体插值、最大检测数和忽略规则也要随评价器固定。参考[官方指标说明](https://docs.ultralytics.com/guides/yolo-performance-metrics/)。

本批不做NMS。手写的两个重叠划痕框会保留，其中一个成为FP，正好说明“重复框需要明确处理”。未来如果模型已经导出包含NMS的结果，不能不加核对再套一次自定义NMS。

分数首先是模型/后处理定义的排序信号，不自动等于“该工件有90%概率不合格”。阈值要在验证集结合漏检/误检成本、复检流程和每类表现选择，再在冻结测试集报告。不能为了测试分数持续调阈值，也不能仅凭本批几个人工框选择现场参数。

## 8. C#部署前必须固定的契约

以下是后续要取得并验证的事实，不是本批已知某个模型的配置：

| 层次 | 必须记录/核对 |
| --- | --- |
| 产物 | 模型来源、任务/代际、文件哈希、标签顺序、导出工具和选项版本 |
| 输入 | 名称、dtype、维数、NCHW/NHWC、固定/动态尺寸、批大小 |
| 图像处理 | 灰度/彩色、BGR/RGB、缩放、归一化、letterbox具体取整与填充值 |
| 输出 | 名称、维数、每维含义、框格式与空间、类别分数/额外objectness、是否已经NMS |
| 还原 | 网络坐标到原图/ROI坐标、裁剪策略及显示坐标变换 |
| 运行 | ONNX Runtime版本、CPU/GPU执行提供器、原生依赖、线程/会话所有权 |
| 业务 | 结果与帧/工件关联、模型/标签/阈值版本、无结果/失败/结果未知的区分 |

不要写“YOLO输出永远是1×84×8400”。有的例子来自特定类别数与尺寸，有的模型额外输出分支或内置后处理，动态尺寸也会改变数量。元数据只能给出部分结构，不能从形状猜出每个通道的语义；还需要导出说明和相同输入的参考数值对照。[官方导出选项](https://docs.ultralytics.com/modes/export/)明确有格式、动态尺寸与NMS等差异。

部署前也应核对代码、权重、数据及导出产物的具体许可与使用场景；转成ONNX不意味着可以跳过来源和许可核查。Ultralytics有[许可说明](https://www.ultralytics.com/license)，本课程不在型号未固定时替项目决定商业许可，也不在本轮自动下载文件或购买授权。
