## 数据访问由谁负责什么

ADO.NET 是 .NET 的数据访问基础 API 家族，不等于某一个数据库驱动或 ORM。提供程序提供 `Connection`（连接）、`Command`（执行 SQL 与参数）、`DataReader`（前向读取结果）和 `Transaction`（一组操作的提交/回滚）。EF Core 等 ORM 在更高层处理映射、变更跟踪和查询翻译；理解底层边界有助于排查 ORM 生成的查询，但不代表每个项目都要手写 ADO.NET。

| 对象 | 责任 | 常见错误 |
| --- | --- | --- |
| `DbConnection` | 开关数据库连接 | 全局共享同一打开连接；连接串泄露 |
| `DbCommand` | SQL、参数、超时 | 把输入拼进 SQL；无限等待 |
| `DbDataReader` | 逐行读取结果 | 未释放 Reader；大结果无分页 |
| `DbTransaction` | 多条写入的原子边界 | 忘记提交/回滚；把长时间外部调用放进事务 |

## 一个需要真实数据库的示例

如果暂时没有 SQL Server，可先完成[SQLite 本地集成验证](/knowledge/programming/csharp/collections/sqlite-integration-test/)：它用内存数据库真实运行参数、Reader 和事务，再回来对照不同提供程序的边界。

以下示例以 SQL Server 为目标，**不是纯 .NET SDK 开箱即跑**：需先安装 `Microsoft.Data.SqlClient` NuGet 包，准备 SQL Server 中的 `Readings(DeviceId nvarchar(64), Value float)` 表，并配置环境变量 `HNOVA_SQL_CONNECTION_STRING`。这里用环境变量仅避免把凭据写入示例代码；生产环境应使用合适的密钥管理和最小权限账号。

```csharp filename="Program.cs"
using System.Data;
using Microsoft.Data.SqlClient;

string? connectionString = Environment.GetEnvironmentVariable("HNOVA_SQL_CONNECTION_STRING");
if (string.IsNullOrWhiteSpace(connectionString))
    throw new InvalidOperationException("请先设置 HNOVA_SQL_CONNECTION_STRING");

string deviceId = "pump-A"; // 实际项目可来自用户输入，但只能作为参数值
using var connection = new SqlConnection(connectionString);
await connection.OpenAsync();

using var command = connection.CreateCommand();
command.CommandText = "SELECT DeviceId, Value FROM Readings WHERE DeviceId = @deviceId";
command.CommandTimeout = 15;
command.Parameters.Add("@deviceId", SqlDbType.NVarChar, 64).Value = deviceId;

using var reader = await command.ExecuteReaderAsync();
while (await reader.ReadAsync())
{
    string id = reader.GetString(0);
    double value = reader.GetDouble(1);
    Console.WriteLine($"{id}: {value}");
}
```

参数化命令把用户数据当值，而不是当 SQL 源代码解析；它是防 SQL 注入的基本要求。参数不能替代**表名或列名**之类的 SQL 标识符：动态标识符必须按允许列表选择，不要直接拼接用户文本。数据库字段类型、参数类型/长度、大小写排序规则和空值处理也要与真实表结构一致；示例只覆盖了非空两列。

## Reader、分页与异常边界

`DbDataReader` 是前向读取接口，不会自动把所有行装进列表；但服务端仍可能为查询排序、扫描或锁定资源。只在需要的时间内保持连接/Reader 打开，大结果需要按稳定键分页或分批处理，不能把“Reader 是流式”误解为“查询没有数据库成本”。Reader 未关闭时，同一连接上能否继续执行其他命令取决于提供程序和配置，不应依赖偶然行为。

能处理的数据库异常应在应用边界分类记录并给出合适反馈，不要把包含连接串或完整 SQL 参数的异常直接返回给用户。连接池通常由提供程序管理；`Dispose`/`using` 是归还和清理使用边界，不等于每次物理断开后重新建 TCP 连接。异步 `OpenAsync`/`ReadAsync` 使等待期间线程可用于其他工作，但不会让 SQL 本身“自动更快”。

## 事务与 ORM 的位置

若要同时写入读数与审计记录，必须决定它们是否属于一个原子操作。事务内的所有命令要关联同一连接及事务；成功才 `Commit`，失败则回滚或在释放未提交事务时由提供程序处理。尽量缩短事务，不把调用外部 HTTP 服务放在数据库事务里等待。具体隔离级别和重试策略取决于数据库及业务一致性要求。

ORM 不是“完全不需要 SQL”：查询是否在服务端执行、是否产生 N+1 次访问、何时保存变更、事务如何划分，都需理解。反过来，简单报表或特定性能路径也可直接使用参数化 ADO.NET。先选清楚持久化要求，再选工具。

## 面试自测与练习

1. 为什么 `WHERE DeviceId = '" + deviceId + "'` 不可接受？参数能否表示表名？
2. `DbDataReader` 与 `ToList()` 在内存和资源生命周期上的差别是什么？
3. 一次操作要写两张表，第一条成功、第二条失败怎么办？事务要覆盖哪些命令？
4. 若没有 SQL Server，也可先画出 `Connection → Command → Reader/Transaction` 的生命周期，再在有测试数据库的环境运行示例；不要拿生产库做练习。

验收标准：能写出参数化查询的骨架，明确需要的驱动/数据库条件，并说清连接、结果和事务的释放边界。
