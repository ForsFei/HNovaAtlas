## 先建立正确的心智模型

同步方法调用后，调用方通常要等它返回；异步方法可先返回一个 `Task`，代表未来完成、失败或取消的操作。`Task<T>` 完成时产生 `T`。`await` 在操作尚未完成时暂停当前异步方法，等完成后继续；它不等于「占着当前线程空等」，也不保证「另开一个线程」。

读文件、网络请求等 I/O 常有等待时间，适合使用原生异步 API。大量纯计算是 CPU 工作：仅把方法标成 `async` 不会让计算并行。要不要使用后台线程或并行计算是另一项设计决策。

## 第一个可运行的异步例子

下面可直接放在控制台项目的 `Program.cs`。`Task.Delay` 是演示非阻塞等待的计时器，不是生产中模拟真实 I/O 的替代品。顶级语句里允许 `await`，编译器会生成合适的入口。

```csharp filename="Program.cs"
Console.WriteLine("开始读取");
string result = await ReadSensorAsync("pump-A");
Console.WriteLine(result);

static async Task<string> ReadSensorAsync(string deviceId)
{
    await Task.Delay(300);
    return $"{deviceId}: 72.5 °C";
}
```

`async` 让方法中可以使用 `await`；返回 `Task<string>` 表示最终有字符串结果。若方法只表示完成而不返回值，常用 `Task`。除事件处理器等特定入口外，避免 `async void`：调用方无法正常等待并捕获其失败。

## 顺序等待与同时启动

下例的两个任务先启动，再统一等待，因此总耗时接近较慢的那个操作；若在第一次调用后立刻 `await`，再开始第二次，耗时则接近两次相加。这是并发等待，不意味着两项工作由两个 CPU 线程执行。

```csharp filename="Program.cs"
Task<string> first = ReadSensorAsync("pump-A");
Task<string> second = ReadSensorAsync("pump-B");
string[] results = await Task.WhenAll(first, second);
foreach (string result in results)
    Console.WriteLine(result);

static async Task<string> ReadSensorAsync(string deviceId)
{
    await Task.Delay(300);
    return $"{deviceId}: 72.5 °C";
}
```

`WhenAll` 等所有传入任务完成，结果顺序与传入任务顺序一致，而非完成先后。若任一任务失败，等待它会报告失败；不要因为只看到一个被抛出的异常，就以为其他任务没有执行或没有失败。对大量外部请求还需要限制并发度，不能把几万个请求一次全扔给 `WhenAll`。

多任务同时失败、`WhenAny` 只返回先完成的任务，以及 `WaitAsync` 超时后原任务仍在运行的处理责任，见[Task 组合的故障与超时](/knowledge/programming/csharp/concurrency/task-composition-faults-and-timeouts/)。

## 取消是一种协作

`CancellationToken` 由调用方提供，异步方法把它传给支持取消的 API，必要时主动检查。发出取消请求不等于立即强行杀掉工作；实际响应时间取决于操作是否观察到令牌。以下示例约 100 毫秒后请求取消，`Task.Delay` 会抛 `OperationCanceledException`，在入口边界处理即可。

```csharp filename="Program.cs"
using CancellationTokenSource source = new();
source.CancelAfter(TimeSpan.FromMilliseconds(100));

try
{
    await Task.Delay(TimeSpan.FromSeconds(5), source.Token);
    Console.WriteLine("读取完成");
}
catch (OperationCanceledException) when (source.IsCancellationRequested)
{
    Console.WriteLine("操作已取消");
}
```

应用中通常由用户操作、请求生命周期或超时策略决定何时取消。不要在最底层静默吞掉取消；否则上层会误以为工作已完成。

## 真实 I/O、异常与资源归属

对于网络请求，使用现成的异步 API，并从外部传入已管理生命周期的 `HttpClient`。调用方可以设置超时/取消，并在合适边界处理网络故障。

```csharp filename="PageReader.cs"
using System.Net.Http;

public static class PageReader
{
    public static Task<string> ReadPageAsync(
        HttpClient client, string url, CancellationToken cancellationToken)
    {
        return client.GetStringAsync(url, cancellationToken);
    }
}
```

这里只是直接转交一个 `Task`，无需额外写 `async` / `await`。若要在方法内转换结果、局部捕获异常或保证资源作用域，再加入 `await`。`HttpClient` 由调用方管理，`PageReader` 不应擅自释放它。网络故障可能抛 `HttpRequestException`，取消通常表现为 `OperationCanceledException`；具体异常仍应以所调用 API 文档为准。

## 常见误区与练习

- 不要在异步调用链中混用 `.Result` 或 `.Wait()` 来「等一下」：它们会阻塞线程，在某些环境中还可能造成死锁。让等待沿调用链保持 `await`。
- 不要忘记等待返回的任务；一个未被观察的失败可能在真正问题发生后才浮现。
- `Task.Run` 主要用于将 CPU 工作安排到线程池，不是把本来就支持异步的 I/O API 包起来的通用办法。

想进一步解释等待后为何有时回到 UI 上下文、`ConfigureAwait(false)` 到底改变什么，接着读[await 的上下文恢复](/knowledge/programming/csharp/concurrency/synchronization-context-and-configureawait/)。

练习：① 把两项 `Task.Delay` 分别设为 300 与 500 毫秒，先顺序等待再同时启动，用 `Stopwatch` 比较耗时；② 给 `ReadSensorAsync` 增加 `CancellationToken` 参数并传入 `Task.Delay`；③ 让其中一项任务抛异常，观察 `await Task.WhenAll` 的控制流，在调用边界报告错误。验收标准是能解释每段代码中的任务由谁创建、由谁等待、由谁取消，以及错误由谁处理。
