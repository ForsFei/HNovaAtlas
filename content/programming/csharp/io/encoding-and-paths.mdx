## 字符和字节之间必须有编码契约

`.NET string` 存的是文本，不是某种磁盘字节。写文件或网络传输时需要编码为字节，读取时需用匹配的编码解码。UTF-8 是现代文本交换的常见选择；“读出来是乱码”首先检查来源字节、约定编码、是否有 BOM，而不是随意换一个 `Encoding` 猜测。

以下代码可独立运行。它选择无 BOM 的 UTF-8，并对非法字节抛异常；这适合不允许悄悄替换坏字符的输入契约：

```csharp filename="Program.cs"
using System.Text;

var utf8 = new UTF8Encoding(
    encoderShouldEmitUTF8Identifier: false,
    throwOnInvalidBytes: true);

byte[] bytes = utf8.GetBytes("温度,72.5");
Console.WriteLine(utf8.GetString(bytes)); // 温度,72.5

try
{
    utf8.GetString([0xFF]); // 不是合法的单字节 UTF-8 文本
}
catch (DecoderFallbackException)
{
    Console.WriteLine("输入不是合法 UTF-8");
}
```

默认的某些解码配置会把错误序列替换为替代字符；如果你用替换后的文本做签名、身份或业务关键字段比较，可能掩盖源数据问题。反之，日志导入允许有损恢复时，替换策略也可能是有意选择。编码、BOM 与错误回退应由文件格式或协议写明，而不是依赖机器的默认代码页。

## `Path` 处理路径字符串，不自动验证文件

不要手写 `"folder\\file.txt"` 作为跨平台拼接规则。`Path.Combine` 和 `Path.GetFullPath` 使路径基准明确：

```csharp filename="Program.cs"
string baseDirectory = Path.GetFullPath(AppContext.BaseDirectory);
string relativeName = Path.Combine("data", "readings.txt");
string fullPath = Path.GetFullPath(relativeName, baseDirectory);
Console.WriteLine(fullPath);
Console.WriteLine(Path.GetFileName(fullPath)); // readings.txt
```

`GetFullPath(relativeName, baseDirectory)` 不依赖后来变化的当前工作目录；它只是把路径规范化，**并不保证文件存在、可访问或位于允许目录的物理边界内**。当文件名来自用户时，必须单独设计路径授权：拒绝绝对路径与 `..` 越界，检查规范化后的范围，并考虑符号链接、大小写规则、并发替换等平台细节。简单的字符串前缀检查不能成为完整安全证明。

文件扩展名也不证明内容格式，`Path.GetExtension` 只能帮助选择处理流程。真正解析 CSV、JSON 或图片时还要校验输入内容和大小；文件系统操作仍可能在检查之后失败。

## BOM、换行和文本格式边界

UTF-8 BOM 是可选的字节前缀，不属于普通文本内容。读写双方必须约定是否允许；`StreamReader` 可以配置是否检测常见 BOM。换行在不同环境可能是 `\r\n` 或 `\n`，若文件是跨平台协议应明确规定输出格式，不用 `Environment.NewLine` 默默决定。若做字节级校验、哈希或签名，BOM 与换行差异都会改变结果。

## 面试自测与练习

1. 同一个 `string` 用 UTF-8 与 UTF-16 编码，得到的字节数一定相同吗？
2. 默认替换非法字节与严格抛错各适合什么场景？
3. `Path.GetFullPath` 能否单独防止用户借符号链接访问允许目录之外的文件？

验收标准：能给出文本格式的编码、BOM、换行和失败策略，并区分路径规范化与访问授权。
