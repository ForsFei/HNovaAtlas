前几课让单条 NG 的读取、证据下载和复核更完整。操作员开始一天的处理时，还需要先找到哪些记录尚未复核。这一课加入「复核状态」筛选，把查询、打开详情和提交结果连起来。

## 1. 从待复核记录开始

按第 4 课配置本地练习账号并启用复核，前端运行 `npm run dev:review`。选择一个有 NG 记录的数据库。 [启动复核练习](/knowledge/web/full-stack/ng-review-and-authorization/)

打开 [待复核 NG 列表](http://127.0.0.1:43112/?result=NG&reviewStatus=pending)。也可以从「复核状态」下拉框选择待复核或已复核。选择状态时，界面会使用 NG 结果，并回到首页。

| 状态 | 查询含义 |
| --- | --- |
| 全部 | 使用原来的检测结果筛选 |
| 待复核 | 原始结果为 NG，且没有对应的保存复核 |
| 已复核 | 原始结果为 NG，且已经有对应的保存复核 |

复核员把一条 NG 判为误判后，它仍属于原始 NG 的已复核记录。机器检测结果和人的复核结论分别保存，方便日后追溯。

## 2. 在数据库里判断复核是否存在

接口增加可选的 `reviewStatus=pending` 或 `reviewStatus=reviewed`。后端启用复核功能后，才允许使用这个条件。普通列表和 CSV 共用 EF Core 查询，计数和分页都基于同一组筛选。

数据库通过关联周期 ID 查询 `Reviews` 是否存在记录。概念上，待复核条件如下。

```sql
WHERE Inspections.Result = 'NG'
  AND NOT EXISTS (
    SELECT 1 FROM Reviews
    WHERE Reviews.InspectionId = Inspections.Id
  )
```

`Reviews.InspectionId` 是主键，查询可以按周期定位对应复核。存在判断也能避免关联表返回多行时重复展示一条检测记录。 [SQLite EXISTS](https://sqlite.org/lang_expr.html#the_exists_operator) · [EF Core 查询与索引](https://learn.microsoft.com/ef/core/performance/efficient-querying)

## 3. 让分页、详情和导出保持对应

页码列表和游标列表都支持复核状态。游标会把状态记入查询范围，拿待复核的游标去请求已复核时，接口返回 400。切换筛选会重建列表，从新条件的首页开始。旧版不带这项筛选的游标仍能继续原来的查询。

成功提交复核后，详情通知上层刷新当前状态列表。页码列表重新查询，游标列表从新首页开始。因此，这条记录会移出待复核列表，而右侧或下方的详情继续展示刚保存的结果。提交响应丢失后，如果通过核对查到了保存结果，也会触发同样的刷新。

CSV 导出继续使用当前工位、时间范围、检测结果和复核状态。选择待复核时，导出的范围就是查询时仍待复核的记录。

## 4. 对照完成一次操作

可以准备同一工位的两条未复核 NG，先选择「加载更多」展开它们。打开一条详情并提交，检查三个位置：

1. 待复核表格移除已处理记录。
2. 当前详情继续显示保存的结论、复核人和时间。
3. 切换到已复核后，可以重新查到刚才的周期。

这份列表是每次查询时的结果。多人同时操作时，另一位复核员仍可能先保存同一条记录，提交时继续由第 31 课的冲突处理展示实际保存结果。 [双用户复核冲突](/knowledge/web/full-stack/review-conflict-and-unsaved-draft/)

## 5. 跑接口与浏览器验收

```powershell
dotnet build examples/web-quality-trace/lesson-03
node examples/web-quality-trace/lesson-03/verify.mjs --review-filter
```

接口验收对照待复核、已复核和 CSV，检查游标范围变化、旧游标兼容，以及复核功能关闭时拒绝使用该筛选。

前端目录的 `npm run test:e2e` 会展开两条待复核记录，提交其中一条，检查列表更新、详情保留和 CSV 内容。它还会切换到已复核，用页码方式查看，再刷新页面确认 URL 能恢复筛选。
