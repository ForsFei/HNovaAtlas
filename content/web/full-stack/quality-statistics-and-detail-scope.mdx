有了可查询的检测和复核记录，本课增加质量统计。先明确每个数字的口径，再写聚合SQL，最后连接已有明细页面。管理台中的“质量统计”对三个角色均开放。

## 1. 先定义分子和分母

| 指标 | 定义 |
| --- | --- |
| 检测总数 | 当前工位及导入时间范围内的检测记录数 |
| NG数 | 其中原始检测结果为NG的记录数 |
| NG率 | NG数 ÷ 检测总数 |
| 待复核数 | 原始结果为NG，且尚无已保存复核记录的数量 |

误判复核不会把原始检测结果从NG改成OK，所以它会减少待复核数，但不会减少这里的原始NG数。若业务想看“复核后不良率”，那是另一个指标，不能悄悄换掉现有分子。

空范围的NG率返回null，页面显示“无数据”，而不是显示0%暗示有一批全部合格的检测。

## 2. 时间沿用导入时间UTC

接口为 GET `/api/management/statistics`，接受 station、since、until。时间格式仍为毫秒精度的UTC字符串，开始包含，结束不包含：

```text
since=2026-11-12T00:00:00.000Z
until=2026-11-13T00:00:00.000Z
```

这统计的是进入追溯数据库的时间，不是设备采图时间或生产节拍时间。迟到导入的历史证据会进入当前导入时间对应的范围，页面明确展示该口径。

界面继续复用 TimeRangeForm，用户填写本地时间，提交时转换为UTC。服务再次解析并检查顺序，非法范围返回400。

## 3. 在数据库中聚合

先用同一组筛选构建查询，再按工位分组。每组分别计算总数、NG和未复核的NG；待复核通过 Reviews 的存在性判断完成。

```csharp
query.GroupBy(i => i.Station).Select(g => new {
    Station = g.Key,
    Total = g.Count(),
    Ng = g.Count(i => i.Result == "NG"),
    Pending = g.Count(i => i.Result == "NG" &&
        !db.Reviews.Any(r => r.InspectionId == i.Id))
});
```

这部分由 EF Core 转换成一条聚合查询，取得每组结果后在内存求总和。总卡片和表格来自同一批分组结果，没有分别请求多个可能处于不同时刻的计数接口。

后续新增检测或复核会让下一次统计发生变化。页面不是固定报表快照，也没有宣称与数秒后打开的明细完全冻结在同一个时刻。

## 4. 先用可读展示解释数据

页面显示检测总数、NG数、待复核数和NG率，再用工位表格显示对应分项。比例使用原生 meter，旁边保留具体百分数，避免只有颜色或长短。

没有数据时仍能读到“无数据”。切换统计范围后先清除旧结果，显示处理状态；失败时显示错误，不让旧数字冒充新条件的结果。

工位选项合并已配置工位和历史检测编码。停用工位的历史数据仍计入统计；新增但没有检测的工位可以被选择，结果为零。

## 5. 从统计回到明细

“查看统计范围明细”把当前 station、since、until 传给追溯页，同时清除原来的 result、reviewStatus、page、id 和游标模式。

这样明细先展示统计分母所对应的全部检测，再由用户按需要选NG或待复核。每页数量是浏览偏好，继续保留。

如果直接保留上一次明细里的“只看NG”条件，统计总数可能是100，而跳转后的列表只有10条，容易被误认为统计错误。显式清除不属于统计范围的旧条件可以避免这种混淆。

## 6. 验收用明确数据核对边界

接口夹具包含一条NG和一条OK，总数2、NG数1、NG率0.5。提交NG复核后待复核从1变成0，NG率仍为0.5。

时间边界夹具将NG设为12日零点、OK设为13日零点。查询12日开始、13日结束时只包含NG，验证开始包含与结束排除。不存在的工位返回零条和null比例。

浏览器验收确认50.0%的显示、无检测工位的“无数据”，以及跳到相同工位明细后显示空结果。管理查询依然受服务端会话授权保护。

复习：误判复核为什么不改变原始NG率？为什么零条记录的比例与0%不同？若要统计采图时间，需要先补哪些可信字段和口径，而不是只改页面标题？
