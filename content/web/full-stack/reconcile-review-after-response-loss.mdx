第 31 课处理了明确返回 409 的提交。还有一种情况，服务器已经提交事务，但浏览器在收到响应前断开连接。页面只能知道自己没有拿到完整结果，操作员需要先读取已保存记录，再判断是否继续提交。

本课给复核区加入「核对提交结果」。遇到网络异常、5xx 或不完整的成功响应时，页面保留本次提交草稿，并提供查询入口。

## 1. 从当前详情查询已保存结果

沿用第 4 课的复核账号、带 NG 证据的数据库和 React 复核模式。 [启动复核练习](/knowledge/web/full-stack/ng-review-and-authorization/)

点击「提交复核」后，如果响应丢失，页面显示本次提交的结论和说明。此时点击「核对提交结果」，前端读取当前会话，再 GET 该周期的复核记录。

| 查询结果 | 界面与后续操作 |
| --- | --- |
| 已保存记录存在 | 展示结论、说明、复核人和时间，用户可以与草稿对照，核对后清除草稿 |
| 暂未查到记录 | 保留草稿和核对按钮，恢复提交表单，允许稍后再查询或重新提交 |
| 查询本身失败 | 保留草稿和核对入口，显示读取错误 |
| 会话已经退出 | 提示登录，登录后再查看已保存结果 |

读到记录后，应核对实际保存的提交人和内容。其他复核员也可能在这段时间内完成了提交。查询为空只描述这次读取时的结果，原请求仍可能在处理。后续重新提交时，数据库仍通过周期主键保证只接收一条复核。

## 2. 把不完整响应也当成待核对

网络层报错，可能发生在请求发出之前，也可能发生在服务端写入之后。5xx 也需要结合保存结果判断。即使 HTTP 状态成功，如果响应体丢失或字段格式不符合约定，页面仍需保留草稿，等待核对。

前端会校验复核结果的结论、说明、提交人和时间。确认得到有效保存结果后，才结束正常提交流程。发生不确定情况时，由用户发起 GET 查询。HTTP 对非幂等请求的自动重试有专门约束，调用方需要知道操作语义以及重复执行的后果。 [HTTP 请求重试](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)

本系列的一次性复核依靠数据库主键处理重复写入。MES 场景中需要复用原回执的投递流程，则在第 7 课使用幂等键和持久回执。 [MES 幂等投递](/knowledge/web/full-stack/http-mes-idempotent-delivery/)

## 3. 在浏览器中丢掉一份真实成功响应

在前端目录运行验收。

```powershell
cd examples/web-quality-trace/lesson-02
npm run test:e2e
```

验收把一条 POST 真正发给 ASP.NET Core，并确认服务器返回 201，随后在响应进入页面前中断它。页面应保留待核对草稿。点击核对后，GET 能读到数据库已保存的结果。脚本同时计数，确认这一步没有再次发送 POST。

另一个场景会在 POST 到达后端之前中断请求，并模拟一次 503。核对时仍查不到记录，表单保留原说明。随后明确重新提交，服务器才保存这条复核。两条路径帮助区分「没收到响应」和「已查明当前保存结果」。

草稿仍保存在当前详情组件内。关闭详情或刷新页面后，可以重新进入该周期，登录并读取持久化的复核记录。

复习时试着解释，如果 GET 暂时查不到记录，为什么原请求仍可能随后完成？再次提交时，最终由哪一层决定是否插入成功？
