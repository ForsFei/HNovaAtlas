前两课让自己的提交更新待办列表，并处理末页缩小。多人复核时，另一个浏览器会话也可能完成当前列表中的记录。本课加入「刷新复核列表」，让操作员在当前筛选下重新查看待办。

## 1. 在两个独立会话中观察变化

沿用第 4 课的复核环境，用普通窗口和 InPrivate 窗口分别登录 alice 和 bob。选择一个有未复核 NG 的工位。 [启动复核练习](/knowledge/web/full-stack/ng-review-and-authorization/)

alice 打开该工位的待复核列表，bob 打开其中一条记录并提交。bob 看到保存成功后，alice 原先读取的列表仍可能包含这条记录。此时点击「刷新复核列表」，页面会重新请求相同的筛选条件。

| 当前模式 | 刷新时的行为 |
| --- | --- |
| 页码分页 | 重新读取当前页和最新总数 |
| 加载更多 | 丢弃本轮累计列表与旧游标，从当前筛选的首页重读 |
| 筛选结果为空 | 刷新入口继续保留，便于查询后续变化 |
| 刷新后页码失效 | 使用第 38 课的入口返回有效页码 |

刷新保留工位、结果、复核状态和时间范围，页面地址继续表示这些条件。操作员可以从待复核切换到已复核，确认刚才处理的周期进入了对应范围。

## 2. 复用保存后的刷新机制

第 37 课已经建立了复核变化后的刷新计数。本课的按钮使用同一个入口，增加这份计数，让查询重新执行。

页码列表依靠刷新版本重新请求。游标列表则把刷新版本作为组件标识的一部分，从新首页建立一次读取。这样，已经移出待办范围的记录会按最新查询结果更新，旧游标也随本轮列表结束。 [React 组件标识与状态重建](https://react.dev/learn/preserving-and-resetting-state)

按钮刷新的是复核列表。已经打开的详情继续保持自己的读取与编辑状态。如果其他复核员先保存了该周期，当前用户再提交时，仍会通过 409 处理读取实际保存结果。 [复核冲突与草稿保留](/knowledge/web/full-stack/review-conflict-and-unsaved-draft/)

## 3. 把列表结果和提交裁决联系起来

待复核筛选表示查询时尚无复核记录。读取结束后，其他人仍可以完成同一个周期。因此，列表用于帮助操作员找到待办，最终提交仍由数据库主键约束裁决。

在复核模式中，用户可以主动刷新查看外部变化。在实时模式中，原有定时查询也可能更新列表。刷新请求同样使用前几课的超时、取消和限流处理，操作员可以根据页面提示重试。

## 4. 运行双会话验收

在前端目录执行。

```powershell
cd examples/web-quality-trace/lesson-02
npm run test:e2e
```

脚本用两个独立浏览器上下文隔离 Cookie。第一个会话读取待办，第二个会话以 bob 身份完成复核，再检查第一个会话主动刷新后移除已处理记录。页码和游标模式各验证一次，并检查空结果、已复核筛选和 URL 保留。

复习时想一想，为什么成功读取待办之后，提交时仍可能遇到 409？游标列表主动刷新时，为什么要从首页建立新一轮读取？
